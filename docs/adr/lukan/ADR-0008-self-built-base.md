## 1 背景

沧溟（Cangming）的 `Platform` 与 `Shell` 已经给出基座大部分契约：命令注册、快捷键、上下文键、通知、输出面板、忙状态、偏好、用户习惯、最近文件、文档会话、诊断与崩溃上报。其默认实现以内存版为主，没有 Avalonia 适配，边界与生命周期仍在演进。

若直接依赖这些包，基座的形状会被上游节奏决定：上游改接口，本仓就得跟；上游不成熟的部分，本仓要么等，要么绕。

## 2 决策

1. **基座在本仓自建**：技术内核的七项（主题、语言、插件宿主、宿主壳、共享契约、首选项、用户习惯）由本仓定义并实现。
2. **沧溟只作参考**：契约划分、命名与职责边界参考其 Platform/Shell，不复制实现代码。
3. **继续依赖的沧溟包**：`Cangming.PicoPlugins`（插件内核）、`Cangming.Logs`（日志）、`Cangming.Toolkit` 与 Avalonia/AtomUI 适配、`Cangming.Primitive`。这些是稳定且难以自建的部分。
4. **成熟后上游化**：本仓实现稳定后，把基座能力提交到沧溟，而不是长期分叉。提交时以本仓实现为准对齐接口，不反向改造本仓去迁就上游。
5. **不 fork、不 vendoring**：继续从公开 nuget.org 取包，不为基座单独维护沧溟分支。

## 3 后果

- 基座的演进节奏由本仓掌握，插件、功能与业务不被上游阻塞。
- 基座需要自己承担测试与文档成本；这部分不能省。
- 上游化时存在一次接口对齐的迁移成本，需要提前保持命名与语义可迁移（不依赖本仓特有的捷径）。
- `ImageLyre.Contracts` 里的基座契约必须保持与 UI 工具包无关，便于将来整体上移。

## 4 备选方案

| 方案 | 结论 |
| :--- | :--- |
| 直接依赖 `Cangming.Platform` 与 `Cangming.Shell` | 否：实现不成熟，绑定上游节奏 |
| fork 沧溟并长期维护 | 否：维护成本与同步成本都高 |
| 完全自建、不参考 | 否：重复设计，且失去与沧溟生态一致的机会 |
