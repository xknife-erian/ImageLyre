## 状态

Accepted，2026-11-18 由项目负责人拍板，作为与数据兼容并列的交互层原则。

## 背景与约束

本项目的目标用户是有 ImageJ 使用经验的科研人员，迁移成本不只在数据格式，也在肌肉记忆：菜单位置、工具栏分组、ROI 绘制手势、测量流程、快捷键与结果表操作都已被长期训练。若界面虽然现代但操作序列全部改写，用户就得在两套工具之间来回切换，迁移意愿会明显下降，功能再全也难以替代。

另一方面，1.0 已明确不继承 ImageJ 的技术包袱：不兼容 Java 插件、不实现 IJM 宏、不复刻 Swing 视觉，插件与内核按新架构重建。因此「保留操作习惯」必须与「不复刻旧实现」划清界线：保留的是用户可见的操作序列与术语，不是外观、控件实现或运行时。

## 决策

交互层以「操作习惯延续」为默认，具体约束如下：

1. 核心路径的菜单层级、工具分组、鼠标手势与快捷键尽量与 ImageJ 对齐，包括打开图像、缩放与平移、绘制与编辑 ROI、测量、导出 CSV 与浏览栈。
2. 术语沿用 ImageJ 的常用叫法，例如 Selection/ROI、Measure、Analyze Particles、Stack、LUT；新造概念必须能在 ImageJ 中找到对应，或给出迁移说明。
3. 视觉与控件现代化不视为违背：AtomUI 的主题、布局与动效可以与 ImageJ 不同，但用户完成任务的操作序列与结果位置应当可预期。
4. 无法保留的习惯必须显式登记：在设计文档中写明原因与替代路径，并在首次使用的迁移提示中说明，不允许静默改变。

## 备选方案

- **完全自由设计**：界面更现代，但迁移成本高，用户需要重新学习，否决。
- **像素级复刻 ImageJ 界面**：与 AtomUI 一等公民及跨平台现代化冲突，复刻 Swing 观感也没有价值，否决。
- **双模式界面（经典 / 现代）**：维护两套界面与两套操作语义，长期成本高且容易分裂，否决。

## 后果

正面后果是迁移与培训成本下降，ImageJ 的功能对照、文档迁移与用户经验都能复用，替代 ImageJ 的主张才站得住。

负面后果是交互设计空间受约束：命令面板、上下文工具栏这类更现代的交互，必须以不破坏既有核心路径的方式引入；部分场景要在「更顺手」与「更熟悉」之间取舍，验收也需要真实用户的操作测试。

缓解办法是把核心路径列为强制项、非核心路径列为建议项，把操作习惯写进准入清单，新交互先以可选方式提供，再评估是否替换默认路径。
