# ADR-0001：docs 文档体系采用按用户分目录的归属结构

## 背景与约束

由于ImageLyre的模块边界横跨内核、通信、插件沙箱与外部适配等多个方向，多位同事在同一时间段内并行推进各自子系统，因此文档的产出节奏彼此独立、主题又频繁交叉；在此前提下，若文档按主题在类型目录下平铺存放，则每个人的第一份 ADR、第一份计划都倾向于占用同一个序号，文件名冲突与互相覆盖便会在合并时集中爆发，而逐次协调序号又会把起号这一纯形式动作变成跨人排队。

与此同时还存在两条硬约束：其一，文档必须能长期检索，因此存放位置要能从“体裁”与“归属”两个维度同时定位；其二，Markdown 文件在 Git 中的重命名与移动会丢失引用锚点的稳定性，因此结构一旦确定就不宜频繁调整。

## 决策

`docs/` 采用「先按体裁分类、再按用户归属」的两级结构，即所有文档的路径固定为 `docs/<类型目录>/<用户名>/<文件名>`，其中类型目录为 `adr`, `analysis`, `daily`, `design`, `plans` 五者之一，用户名与 Git 账号一致；序号仅在用户目录内唯一，而引用他人文档时必须写出含用户名的完整路径。

## 备选方案

| 方案 | 重名与编号冲突 | 引用与检索成本 | 结论 |
| :--- | :--- | :--- | :--- |
| 类型目录下全部平铺 | 每个新文档都要与他人比对序号，冲突概率随人数线性上升 | 检索成本最低，但合并冲突频繁 | 不采用 |
| 只按用户分目录、不分体裁 | 冲突消解彻底 | 需靠文件名猜体裁，日志与决策混在一处 | 不采用 |
| 类型目录下加用户子目录（本决策） | 冲突在路径层面被消解，起号零协调 | 引用需写全路径，略长但语义明确 | 采用 |
| 平铺并用 `<用户名>-` 前缀命名文件 | 冲突消解彻底 | 文件名变长，且依赖人工维持前缀一致性 | 不采用 |

## 后果

正面后果是新增文档不再需要跨人协调序号，评审时可按用户目录整体审阅某位同事的产出，且“谁维护这份文档”由路径直接给出答案；负面后果是简写引用（如“见 ADR-0001”）在跨用户场景下产生歧义，且用户目录数量随人员增多而膨胀，因此本决策同时以「引用必须写全路径」作为配套约束，把歧义风险压在命名规范一侧。

后续动作包括：在 `docs/README.md` 中登记目录表与命名约定，并在 5 个类型目录下各放置一份本人名下的示例文件，使规则有可参照的实物样本。
