# Mercury 指南全集阅读台账

## 1 为什么要读

Mercury 的 `docs/guide` 是这套插件体系的一手说明书：它写的不是理念，而是"某件事正确做法长什么样、错了会怎样、怎么验证"。本仓直接用同一套内核（PicoPlugins）与同一套槽位模型，因此这些指南对我们不是参考读物，是操作规程。

## 3 已经能落地的结论（先记，勿丢）

1. **契约交出方式**：指南用 `protected override TModule Module => _service;`，`Build` 只在需要按参数产实例时覆盖。本仓的六个模块已开始从 `Build()` 迁到 `Module` 属性（`BusyModule`、`CommandsModule` 已改）。
2. **没有依赖就不写上下文**：`BasePicoModule<T>` 的默认 `BaseModuleContext` 够用，空上下文类属于噪音。
3. **依赖先声明再取用**：`DeclareDependencies` 里只写 `Require`/`Optional`/`After`，运行期从上下文 `Use<T>()` 取。
4. **目录白名单**：根目录只放身份文件（入口、上下文、偏好、错误、csproj），实现全进 `Internal/`。

## 6 23-标识体系 读后记录（2026-11-20）

**语义确认**。OwnerId 是类型名，用于权限与诊断归组；OwnerInstance 是运行期实例标识，只用于释放与 Detach，不落库。本仓 SlotAttachmentEntry 的两个字段与之一致，此前担心的"混用会让停用即撤失效"不成立，无需改结构。

**三条可直接采信的规定**：

1. 只有 SlotName，没有 SlotKey；完整的三段式是 <区域>[.<用途>][.<方位>]，例如 Driver.Balance.XiPing.Debugger。
2. 声明方、附着方、宿主三处必须逐字一致，不一致分别表现为：声明重名抛异常、附着进 UnresolvedSlot、面板空白。
3. CommandName 用动宾短语、英文、Feature 内唯一；中文或缺失会变成灰显加装配问题。

**本仓的两处偏离**：

- 槽位名现在是 ImageLyre.Menu、ImageLyre.Content、ImageLyre.StatusBar，是"产品前缀 + 单段"，不是指南的"区域 + 用途 + 方位"。它自洽且三处一致，但与我们自己的 WorkbenchSlots 契约放在 WorkbenchSlots 类里这件事叠加后，改名成本低、收益也只是与上游同构。结论：记入待办，不在 A 到 E 的范围内改。
- 附件形态矩阵我们只允许五类且已在 AttachCore 里校验，与指南一致，无需调整。

**一条要补的能力**：指南提到自检窗口按槽位名列出附件与来源，我们只有 Snapshot() 与诊断列表，没有可视化的槽位图。它属于 D 批之后的诊断界面，记入待办。

## 7 24-诊断与自检 读后记录（2026-11-20）

指南给 14 类 SlotIssueKind，我们实现 7 类。少掉的 7 类里 5 类属于不适用而非遗漏：参数与模板分组那套模型我们在迁移时已删（无 WPF 模板配对、附件不带参数），保留枚举只会产生永不触发的分支。

两条该学未做：
1. 问题去重：按槽位 + owner + 码去重，我们的列表是纯追加，反复上报会膨胀。
2. 两个时点各输出一行 Dump：首帧给基线、退出核对订阅归零；我们只有启动一行。

SlotIssue 四字段与指南一致。

## 8 15-菜单模型 读后记录（2026-11-20 部分）

读了 §4 声明式条件。Mercury 的做法是 Feature 实现 IMenuConditionManifest，把"何时可用、何时可见"声明给宿主：

- RegisterEnable(key, unexcepted, mandatory, apply) 与 RegisterVisibility 同形，可见与可用是两条独立通道；
- 条件写的是状态键字符串（如 ExpLoaded:True、Panel:ExpFlowPanel），由 IUIStateService 的 Responser 产出；
- 注册后宿主立刻按当前状态求值一次，菜单初始态就是对的；
- 同一 key 二次注册替换旧订阅，Feature 重启不累积。

本仓现状：菜单附件上是静态的 IsEnabled 与 IsVisible，没有条件、没有状态键服务、没有 UIState 那一层（迁移时按不做权限与不做状态匹配器的判断删掉了）。

结论：**不纳入 A 到 E**。理由是它依赖 IUIStateService 这套状态键生产机制，属于新能力而不是本计划的补齐项；若将来要做，前置是先有状态键服务，再谈条件注册。记入待办。

## 9 14-日志栈 读后记录（2026-11-20 部分）

读了 §3 获取方式。四条约束各有代价：private 防子类顺手用父类字段导致类别错位、static 避免每实例一份、readonly 堵住运行期替换、每类一份避免继承污染。字段名统一 s_logger，类型写 ILogger，类别由 For<T> 的类型参数决定。

**对照本仓**：用法基本合规。Program、BootstrapHostBuilder、PluginStartupPolicy、WorkbenchShell 都是 private static readonly ILogger s_logger，取法分别是 For(typeof(X)) 与 For<T>()，与指南§3.2 的两档入口一致；结构化日志用 [LoggerMessage] 分部方法，符合 §5 的方向。

**一处待统一**：同一仓里 For<T>() 与 For(Type) 混用，指南说新代码首选 For<T>()，For(Type) 只给静态类或没法写泛型实参的场合。我们两个静态类用 For(Type) 是对的，其余能改的可改。

**未读**：§7 禁止事项与 §4 级别规范，下一轮补。

## 10 14-日志栈 禁止事项审计（2026-11-20）

读完 §7 七条禁止与 §8 常见错误，对本仓做了一次静态审计：

| 规则 | 本仓结果 |
| :--- | :--- |
| 插件与公共库不得引用 NLog | 通过。仅 Bootstrap/Logging/LoggingBootstrap.cs 引用 NLog，属引导层，是允许的落点 |
| 不得用继承分发日志器 | 通过。没有基类声明 protected/virtual 的日志属性 |
| 不得每个方法取一次日志器 | 通过。grep 未发现方法内的 LogHub 取用 |
| 日志字段 private static readonly | 通过。七处声明全部是 s_logger 静态字段 |
| 测试工程与工具要先初始化 LogHub | 不适用。现有测试不写日志；tools/Screenshot 也不写 |
| 不得改日志配置与输出路径 | 通过。路径只在 LoggingBootstrap 一处决定 |
| 不得批量改写已有调用 | 通过。没有为统一写法做的批量替换 |

另外记下 §8 里两条会真正咬人的：Error("消息", ex) 编译不过（要写 Error(ex, "消息")），以及把异常拼进消息会导致文件里没有堆栈。
