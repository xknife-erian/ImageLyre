# 项目 docs 目录体系的初始化、补全与升级

本技能管两类同类的事：**新建项目时**把 `docs/` 与它的八个类型目录、规则 README 与七份可复制示例一次铺好；**已有项目在启用 agent 工作模式后发现 docs 不完善时**，先体检出缺口、再补齐目录与规则、并把散落的历史文档归位。两种场合共用同一套骨架与同一份规则，区别只在于前者从零开始、后者必须先看清现状再动手。

八个类型目录分两组：**过程类** `adr/`、`analyses/`、`daily/`、`design/`、`plans/` 回答团队自己的工作过程，按 `<用户名>/` 分目录；**交付类** `spec/`、`guide/`、`reference/` 承接对项目生效的规范、面向使用者的指南与来自外部的参考资料，平铺存放、不按人分。分析类目录的旧名 `analysis/` 仍受支持：体检与迁移建议都按同一体裁处理，既不报非标准也不强推改名；同一项目两种写法并存时提示保留 `analyses/`（复数写法是通行惯例）并把 `analysis/` 下的文档合并进去。新建一律铺 `analyses/`，`analysis/` 只作存量兼容、不再新增。此外还有一项**登记制**：项目自有的额外目录（如 `backlog/`、`audit/`、`reviews/`）与子系统自带的文档目录，在规则 README 的表格里登记职责后即视为合规，不必强行并入类型目录，体检也不再报为问题。

第二类场合比第一类更常见，也更容易出事：已有项目常常带着自己的目录习惯（`docs/plan/`、`docs/AI-daily/<人名>/` 之类），还可能已经写过一份规则 README，因此升级动作必须**先体检、后动手**——先出差距清单，再决定哪些缺口直接补、哪些取舍要人拍板，最后才生成与迁移。

生成物归项目所有：两种场合完成后，项目都可以按自身情况增删目录与规则条款，本技能不做回灌同步，只保证**起点与骨架一致**，不追项目后续的分叉。

## 0. 触发条件与适用范围

触发时机分两类。**其一，新建项目或仓库后的初始化**：用户说「初始化 docs」「建一下项目文档目录」「这套文档规则拷一份过去」。**其二，已有项目的补全与升级**：项目启用 agent 工作之后，用户说「docs 目录不完善」「补充一下文档体系」「把文档归归位」，或 agent 自己发现 docs 缺类型目录、缺规则 README、文档散放在类型目录之外、命名各写各的——此时按第 2.2 节走体检、决策、补齐、迁移四步。

不适用：只是要写某一份文档时，按该文档所属类型与项目的 `docs/README.md` 写即可；要修订既有 `docs/README.md` 的规则条款时直接改那份文件。本技能负责**骨架与规则的完备性**，不负责逐份文档的内容质量，后者按 `csharp-doc-style` 评审。

## 1. 参数

模板中有三处占位符，取值来源如下，由脚本的同名选项传入：

| 占位符 | 选项 | 缺省取值 | 约束 |
| :--- | :--- | :--- | :--- |
| — | `--audit` | 不启用（即生成模式） | 只读体检：产出缺口清单、迁移建议与规则差异，不落盘；无需用户名也能运行，给出用户名后迁移建议会落到具体路径 |
| — | `--no-examples` | 不启用（即铺七份示例） | 只铺规则 README 与八个类型目录，空目录放 `.gitkeep`；交付类目录仍会带上职责自述 |
| — | `--self-test` | 不启用 | 运行工具内置的行为回归自检（在临时目录内进行，不接触目标项目），用于改动工具后自查 |
| `{{用户名}}` | `--user` | 目标仓库的 `git config user.name` | 必须与 Git 账号严格一致，不得用昵称或中文名；取不到时报错要求显式给出 |
| `{{项目名}}` | `--project` | 目标目录名 | 用于规则标题与示例正文 |
| `{{日期}}` | `--date` | 当天 | 示例文件名与正文中的日期 |

## 2. 流程

### 2.1 新建项目：一次铺好

1. **确认目标与用户名**：目标是项目根（不是 `docs/` 自身）；用户名取自 `git -C <项目根> config user.name`，与分支前缀属同一来源。
2. **预演再落盘**：先跑 `--dry-run` 看清将创建哪些目录与文件，确认无误后去掉该选项正式执行：

   ```bash
   <skill_dir>/scripts/init-docs.cs --target <项目根> --dry-run
   <skill_dir>/scripts/init-docs.cs --target <项目根>
   ```

   Windows 上改用 `dotnet run <skill_dir>/scripts/init-docs.cs -- --target <项目根>`；项目名请用 `--proj` 传入（`--project` 与 dotnet 自带选项同名）。

3. **校验生成物**：目录层数与规则一致（过程类五个类型目录、各自的用户目录、`adr/` 下的 `archive/` 与 `deprecated/`，以及平铺的三个交付类目录），且规则 README 里已无残留占位符——`grep -n "{{" docs/README.md` 应无输出。
4. **按项目实情裁剪**：项目不需要某类文档时，删除对应目录并**同步修改规则 README 的目录表与示例索引**，两处必须一致，只删目录而不改表格会让规则与实物对不上；项目另有额外目录时，在「项目自有目录登记表」里登记职责与命名约定。
5. **提交**：按项目约定提交，提交信息形如 `docs: 初始化 docs 文档体系骨架`；分支与提交身份沿用项目既有配置，不要为本步骤切换分支。

### 2.2 已有项目：体检、补全与升级

1. **体检（只读）**：先跑 `--audit` 拿到差距清单——缺哪些类型目录与退役子目录、哪些文档不在应有层级、哪些命名不符约定、哪些目录未登记、有无未登记的子系统文档、既有 README 与本模板差在哪些节：

   ```bash
   <skill_dir>/scripts/init-docs.cs --target <项目根> --audit --user <用户名>
   ```

2. **先决策，再动手**：清单里有三类事不能由脚本替你决定——**非标准目录**（项目自己的 `docs/plan/` 之类，保留并登记还是并入标准目录）、**同义异名目录**（`plan/` 与 `plans/`、`AI-daily/` 与 `daily/`、`definitions/` 与 `spec/` 并存时选哪一个；`analysis/` 是 `analyses/` 的旧名，体检已放行，并存时按提示保留 `analyses/` 并合并另一处）、**既有规则冲突**（项目已有 `docs/README.md` 且与本模板不同，是按节补齐缺失节、还是整体替换）。先问清用户；`--force` 会丢掉项目既有条款，替换前先把现行 README 提交一次存档。
3. **补缺口（幂等）**：去掉 `--audit` 正常跑一次生成，只补缺失的目录、README 与自述，**已存在的文件一律不动**，因此这一步不会碰到任何既有文档。
4. **迁移归位（逐条确认，不自动执行）**：按体检给出的 `git mv` 建议把散落文档移入应有位置，外部资料原件（`*.docx`、`*.pdf` 等）移入 `reference/` 并**保留原文件名**。红线是四条：保留原文件名与原编号，不重命名、不重排序号；不删除文档；不改写正文（升级只做归位与补骨架）；涉及他人目录下的文档先取得同意。一次只搬一类，搬完立即核对引用——引用本应写完整路径，所以 `grep -rn "docs/<旧目录名>" docs/` 能捞到待改的引用。
5. **登记与对齐规则文本**：项目自有目录写进「项目自有目录登记表」，子系统自带文档目录写进「子系统文档目录登记」，然后逐条核对 `docs/README.md` 的目录表与示例索引和实际目录、实际示例是否一一对应；示例没铺就删掉索引节，目录被裁掉就从目录表删行。
6. **提交**：迁移与规则文本的改动单独提交（`docs: 补全 docs 文档体系并归位历史文档`），与业务改动分开，便于回退。

## 3. 生成物

| 生成物 | 回答什么问题 |
| :--- | :--- |
| `docs/README.md` | 规则入口：目录职责、命名约定、归属规则、流转路径、必备章节、退役方式、登记表、附件约定、书写规范、示例索引 |
| `docs/adr/<用户名>/` | 已接受或已实现的决策记录，含 `archive/` 与 `deprecated/` 两个退役子目录 |
| `docs/analyses/<用户名>/` | 具体问题的排查、调研与方案取舍论证（旧名 `analysis/` 仍受支持，并存时保留 `analyses/`） |
| `docs/daily/<用户名>/` | 每日工作记录与阶段小结 |
| `docs/design/<用户名>/` | 当前有效的设计文档 |
| `docs/plans/<用户名>/` | 任务拆解与实施排期 |
| `docs/spec/` | 规范、规格与机器可读的定义文件，平铺存放，另带一份职责自述 |
| `docs/guide/` | 面向使用者与接入者的指南，平铺存放，另带一份职责自述 |
| `docs/reference/` | 来自外部的参考资料，保留原件文件名，另带一份职责自述 |
| 七份示例 | 过程类五类各一份，外加 `archive/` 与 `deprecated/` 的退役登记示例，既可读又可复制 |

规则条款本身写在模板里（`templates/README.md`），生成即成为项目自己的 `docs/README.md`，本技能不重复转述其中的内容，以免两处规则随时间漂移。

## 4. 脚本能力与边界

- **幂等**：已存在的文件默认跳过，只有显式加 `--force` 才覆盖；重复执行不产生差异，因此可用于给已有项目补缺口。
- **只读体检**：`--audit` 不写任何文件，逐项检查八类目录与退役子目录是否齐备、文档层级是否符合各组规则（过程类三层，允许再加一层主题子目录；交付类两层）、命名是否符合约定（`README.md` 作为目录自述豁免）、项目自有目录是否已登记、子系统文档目录是否已在根 README 登记、规则 README 缺哪些节（必备节计入缺口，登记表/附件/子系统三节按建议提示）、示例索引条数与实际文档份数是否对得上，以及既有 README 与模板渲染后的逐行差异。
- **推断与不猜**：能按文件名推断体裁的（`ADR-*`、`DESIGN-*`、`PLAN-*`、日期型命名、外部资料原件）直接给出可复制的 `git mv` 建议；推断不出的标注「目标类型需人工判断」，非标准目录去留与规则冲突取舍一律交人决定。
- **自定位**：工具以自身所在技能目录为基准解析模板，不依赖调用时的当前目录。
- **实现语言**：C#（.NET 10 单文件应用，需机器上有 .NET 10 SDK），首行 shebang 使其在 Linux/macOS/WSL 下可直接执行，Windows 下用 `dotnet run <工具>.cs -- 参数`。之所以不用 bash/python，是因为它由 C# 团队维护，出问题时要能自己读懂与修改。
- **两处命名陷阱**：`dotnet` 驱动层会截走它自己认识的选项——直接执行时 `--help`/`-h` 打印的是 .NET 的帮助而不是本工具的说明，`--project` 会报选项冲突；因此取帮助用 `help` 或 `-?`，传项目名用 `--proj`，或统一在参数前加 `--` 分隔符。
- **自带回归**：`--self-test` 覆盖生成、幂等、体检各现状、登记制放行、参数校验等 40 余项断言，改动工具后先跑它。
- **不静默**：不带参数运行时打印用法并以非零码退出，不会什么都不做地成功返回。
- **边界**：脚本不判断项目是否需要示例、不替你改规则表格、不代为提交、不自动迁移文件，这些都需要按第 2 节逐项确认。

## 5. 边界情况

1. **目标已有 `docs/`**：走第 2.2 节的升级流程，先体检；生成时只补缺失项，不覆盖既有文件。
2. **既有 README 与本模板冲突**：先决定保留项目自有条款还是整体替换；`--force` 覆盖前提交一份现行存档，便于回退。体检时带上与生成时相同的 `--user/--project/--date`，逐行比对才有意义。
3. **项目自带非标准目录**（`docs/plan/`、`docs/audit/` 等）：保留是正当选择，但要在「项目自有目录登记表」里登记职责与命名约定，否则下一轮体检还会再报一次。
4. **同义异名目录并存**：`plan/`、`AI-daily/`、`definitions/` 这类拼写会造成引用与检索各写一套，建议并入各自标准名或登记为同一职责；`analysis/` 与 `analyses/` 是同一体裁的新旧两种写法，并存时保留 `analyses/`（通行惯例）并把 `analysis/` 合并进去。并入时按第 2.2 节第 4 步迁移，保留文件名与编号。
5. **文档散落在类型目录之外**：按体检建议迁移并保留文件名与编号；体裁无法从文件名推断的，先问用户再搬。
6. **外部资料**：厂商手册、协议文档等原件放 `reference/` 且不改名；图片附件按规则放 `docs/assets/`（需在登记表登记）或个人用户目录下的 `assets/`；密钥、授权码一律不得写入 docs。
7. **多子系统仓库**：子系统可自带 `docs/` 或 `~doc/`，但必须在根 README 的「子系统文档目录登记」里写明范围与分工，跨子系统的内容一律收在根 `docs/`。
8. **仓库尚未 `git init` 或未配置 `user.name`**：脚本取不到用户名，会要求用 `--user` 显式给出，不要拿本机其它项目的身份顶替。
9. **Windows 原生环境**：工具是 C#，三个平台通用——Windows 下用 `dotnet run <工具>.cs -- 参数` 调用，WSL 下可直接执行同一个文件。机器上没有 .NET 10 SDK 时工具用不了，此时按第 2 节的人工步骤执行，工具只是加速器。
10. **不需要示例**：用 `--no-examples` 只铺空目录与规则 README，空目录会放 `.gitkeep` 以便入库；此时规则 README 的示例索引节需要手动删除或改写。
11. **升级期间不夹带正文整改**：归位与补骨架是结构动作，正文质量整改属另一件事，混在一起会让评审分不清哪些是搬迁、哪些是改写。

## 6. 自检清单

- [ ] 生成物含过程类五个类型目录与各自的用户目录（`adr/` 下含 `archive/` 与 `deprecated/`），以及平铺的 `spec/`、`guide/`、`reference/`
- [ ] 交付类三个目录下没有用户名子目录，且各自带一份职责自述
- [ ] 规则 README 中无残留占位符（`grep -n "{{" docs/README.md` 为空）
- [ ] 示例文件的目录与规则 README 的示例索引逐条对应
- [ ] 用户名与 `git config user.name` 一致，没有出现昵称、缩写或中文名
- [ ] 若删改过类型目录，规则 README 的目录表与示例索引已同步
- [ ] 项目自有的额外目录已在「项目自有目录登记表」登记职责与命名约定，子系统自带文档目录已在「子系统文档目录登记」登记
- [ ] 升级场合：重跑 `--audit` 后缺口与待迁移计数已归零，或剩余项均为已登记的目录
- [ ] 升级场合：迁移用的是 `git mv`，文件名与编号未变、外部资料未改名、正文未改，且 `grep -rn "docs/<旧目录名>" docs/` 无残留引用
- [ ] 升级场合：涉及他人文档或整体替换规则前已取得确认
- [ ] 若改动过本技能的工具，`--self-test` 已跑过且全绿
- [ ] 已按项目约定提交，未为本步骤切换分支
