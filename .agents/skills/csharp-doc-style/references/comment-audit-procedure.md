# 注释风格审计的完整流程

技能自带 `scripts/scan-remarks.cs` 只覆盖「单段正文超行」一条判据。整仓审计还需另两类尺子与一道隔离闸门；顺序固定，颠倒了会重复做功。

## 1. 先取数字（改前基线）

```bash
# 段落超标（技能自带，权威）
"<skill_dir>/scripts/scan-remarks.cs" --max 4 <源码根>
# summary 多句 / 中文标签粘连 / 落款与散文编号（本技能补充脚本）
"<skill_dir>/scripts/scan-doc-comments.py" --max-summary-lines 2 <源码根>
# XML 结构坏与 cref 解析失败（缺 param 也在这里暴露）
dotnet build <工程>.csproj --no-incremental -v q --nologo | grep -E "warning CS15(70|73|74|91)"
```

三类计数当场记下，作为整改后的对照；同时把「哪些文件本来就干净」记下来，避免整改顺手改到无关文件。注意 `CS1570/CS1574` 的口径是**按目标框架重复计**，同一个文件在 `net8.0;net10.0` 双目标工程里会出现两次，去重后才是真实处数；也可能全部来自某个被引用工程而不是本次要改的工程，看路径再判。

## 2. 按重量分层改（顺序不能反）

1. **结构层**：落款与日期注释整块删；`<br/><br/>` 造段改 `<para>`；三条以上并列的「1. 2. 3.」散文改 `<list type="number">`；超载 summary（四句以上或五行以上）拆成一句 summary + 分段 remarks。这一层动的是注释骨架，改完行号会漂，所以必须排在句法层之前。
2. **句法层**：其余写成两句的 summary 逐条收敛（第二句移入 remarks / 合并成复合句 / 与 param 重复则删）。
3. **标点层**：中文与内联标签之间的半角空格统一补齐，最后跑一次补充脚本归零。

两层拆成两张卡更稳：第一张动骨架、第二张扫尾，各自都能独立复核；挤在一张卡里，句法改动会淹没结构改动，review 读不出夹带。

## 3. 只改注释的隔离闸门（必跑）

注释卡最常见的失败不是风格，是**顺手改了代码**：实测形态是在注释卡里把一个类的命名空间改掉，包自身能编、消费方的样例全红。两道检查缺一不可：

```bash
# 闸门一：diff 里除注释行外必须为空（块注释 /* */ 与 /// 都要放过）
git diff -U0 | grep -E "^[+-]" | grep -vE "^(\+\+\+|---)" \
  | grep -vE "^[+-]\s*(///|//|\*|/\*)" | grep -vE "^[+-]\s*$"
# 期望：无输出（唯一的合法例外是被删注释块内注释掉的旧签名）

# 闸门二：必须构建消费方，不只构建被改的包
#   注释改动不会让包自身报错，但命名空间/类型被挪动只在样例侧炸
```

闸门一的朴素写法 `grep -v '^\s*//'` 会产生假阳性——块注释 `/* */` 不在其覆盖内，别据此误判「改了代码」。

## 4. 非 UTF-8 源码

老仓里常见 GB18030 中文注释文件，`file -i` 报 `iso-8859-1` / `unknown-8bit` 而非 UTF-8。改这类文件必须保持原编码：用能保留编码的编辑器/脚本，改完 `file -i <路径>` 复核一次。编码被转成 UTF-8 时，git 会把整文件标成重写，本可三行的改动变成几百行 diff，审查彻底失效。补充脚本已对编码回退解码，扫描它不会中断。

## 5. 判定为不违规的三种灰区

- `<returns>` 里描述返回元组形状的括号（如 `(true, 耗时毫秒)`）：括号包的是代码元素，保持半角；改全角会让读者当成散文、丢掉「这是值形状」的信号。
- 单句 summary 跨三行：行数不是判据，句数才是；一句话写三行合规。
- 枚举取值并列（`A` / `B` / `C` 各为同位语）：允许顺排，不必强改 `<list>`。

## 6. 收口

整改后重跑第 1 节三条命令，三类计数必须归零（或逐条说明为何保留），并对照改前基线贴出前后数字；再把「代码零改动」的闸门输出一并交上去。只有数字 + 闸门同时成立，这张注释卡才算完。
