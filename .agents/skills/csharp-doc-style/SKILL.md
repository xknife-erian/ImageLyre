#### 0. 触发条件与适用范围
-   **何时加载**：当任务涉及新建/修改 C# 代码注释、编写/评审 XML Doc、生成接口契约说明、对已有注释进行风格合规性检查，以及编写/评审技术文档（ADR、Plan、Design、规范、README 等技术正文）时，必须自动激活本技能。
-   **不适用场景**：纯配置文件（`.json`/`.xml`）、无业务逻辑的自动生成代码、以及非 C# 语言文件的代码注释不强制应用本规范，但技术文档类内容不区分项目语言一律适用；**面向用户的界面文案（分组标题、按钮、提示语、工具提示、行内说明）不适用本规范**，那走 `user-facing-copy` 技能：界面要短句直给、不用复合长句，也不允许把类型名、契约成员名与出处塞进去；对于团队内所有手写 C# 源码（含旧代码重构），无论新旧均须追溯适用，其中旧注释的追溯整改应在专门重构任务中执行、不得混入功能改动以避免评审噪音，而功能改动直接触及的注释须当场合规；markdown 文档中代码块内的内容视为代码元素，按第 4 节处理而非按正文句式处理。
-   **完成判据**：注释或文档工作的完成以第 7 节自检清单全部通过为唯一判据，Agent 在生成或修订注释或文档后必须执行该清单并据此整改。

#### 1. 核心原则：以长句承载复杂逻辑
-   **核心目标：去 AI 化（首要原则）**：本规范的首要目标是消除 AI 生成痕迹，因为 AI 生成的文档最典型的特征就是大量短句，阅读时节奏过于碎片化，不符合人类自然的阅读思维，读者在这种节奏里抓不住论证脉络；本节及其后各节的细则都是实现该目标的手段，故当某条形式细则与“读起来是否像人写的完整论述”发生冲突时，一律以本原则为准。
-   **强制复合句优先**：凡描述条件、因果、时序、权衡等含逻辑关系的技术事实，必须使用包含从句、介词结构或并列连词的复合长句；禁止将完整逻辑链拆解为多个孤立短句。
-   **信息单元不可分割**：一个完整的业务规则、设计决策或行为契约必须在一个句子内表达完毕，句号仅落于语义真正闭环之处，而非呼吸节奏或视觉换行点。
-   **列表项须为完整长句（论证性内容）**：当列表用于阐述多个独立但各自复杂的论点时，每个条目必须是包含逻辑连接的复合句；禁止以短语、碎片或孤立短句充当论证性列表条目。
-   **列表形式本身允许保留**：有序与无序列表（含文档中的 Word 自动编号列表、Project 类任务列表）都是正当且常常更有力度的表达形式，优质列表比顺排文字更能承载并列论证，因此去 AI 化针对的是碎片化短句而非列表形式，禁止为规避 AI 腔而把本适合列表的并列内容强行拉平成段落；本条真正约束的是列表项的内部质量——每一项都必须是逻辑通顺、语义完整的句子，而不是短语、半截话或孤立短句。
-   **执行性清单豁免**：仅当列表作为操作步骤、自检项或枚举无内在逻辑关系的原子动作时，允许使用简洁短句；此豁免不适用于任何解释“为什么”或“如何工作”的论述性内容。
-   **反向护栏：禁止硬抻单点事实**：对于无逻辑依赖的单点事实（如字段用途、简单赋值、纯命名约定），允许使用清晰短句；本规范旨在防止逻辑拆碎，而非强迫所有陈述都成为复合句。
-   **句内结构与段落结构互不替代**：本节约束的是**句子内部**的表达，即"一段论证不得由多个孤立短句拼成"；它与第 3 节约束的**段落与列表**是两个层次，因此"禁止孤立短句"不构成拒绝分段、拒绝列表化的理由——先按第 3 节把论点分层，再让每一段、每一条列表项各自成为符合本节的完整逻辑句。

#### 2. 长句构造要求
-   **显式逻辑连接**：必须使用“当……时”“由于……因此”“尽管……但”“除非……否则”等连接结构明确子句间依赖关系，禁止仅靠语序暗示逻辑。
-   **修饰成分嵌入主干**：限定条件、适用范围、例外情况应作为定语或状语嵌入句子主干，而非另起一句补充说明。
-   **长度服从逻辑闭环**：只要语法正确、逻辑清晰、无歧义，单句长达数十字是常态；具体长度由信息完整性决定，不以固定字数阈值判断可读性。
-   **避免伪长句**：禁止用逗号串联多个独立主谓结构形成流水句；真正的长句必须有明确主干与从属关系，而非简单拼接。
-   **长度上限：不得为长而长**：“长度服从逻辑闭环”指的是该长才长，而非越长越好，语义一旦闭环，继续追加的限定、从句与连接词只增加阅读成本而不增加信息，故句子不宜过度冗长；判据是能否一口气读完即解其意，当一句话嵌了多层从属、需要回头重读才能确定主干与指代关系时，就必须拆成多句或按第 3 节分层，不得以“规范要求长句”为由把它留着。

#### 3. 结构分层：分段与列表
-   **段落长度上限**：单一 `<remarks>` 内的一段连续文字不得超过约 4 行源码（约 4×60 字）；超过即须按论点拆分，因为读者的困难几乎从不来自句长，而来自一个屏幕高的连续文字块。
-   **分段必须用 `<para>`**：段落之间以 `<para>` 包裹，因为 XML 文档中的空行不产生段落边界，只有 `para` 元素才在 IDE 提示与生成文档里真正断段；纯源码留空行只能骗过编辑器，不算分段。
-   **列表化判据**：并列要点达到三条及以上，或各要点各有独立依据（不同寄存器、不同手册位置、不同契约条目）时，必须改用 `<list type="number">`（有序，用于步骤、优先级、互斥规则）或 `<list type="bullet">`（无序，用于并列事实），禁止以“其一……其二……其三……”一类顺排文字代替列表。
-   **列表化的豁免**：若并列各项是同一枚枚举的取值，或彼此为同位语式的分项说明（各项各自本就是一句完整判断、且不携带独立依据），则允许仍以顺排承载，此时做到分段即可；本条针对的是“各要点各自需要论证”的情形，而非把枚举列举也硬改成列表。
-   **依据不重复搬运**：当某项依据已由同一文件内更贴近事实的来源承载（枚举成员摘要、描述符字段注释等）时，上层说明只须指出结论并指向该来源，不得把依据抄成第二处真源，因为两处同义文字一旦分头演进就会互相矛盾。
-   **计数以枚举为准**：文档或注释中出现“N 段”“N 项”一类计数时，其数值必须与紧随其后的枚举逐项对应；两者不一致时以枚举为准并修正计数，不得为迁就一个数字而改动被枚举的类型或形状。
-   **段落行数的计数口径**：统计单段行数时只计说明性正文行；`<summary>`、`<remarks>`、`<param>`、`<returns>`、`<exception>`、`<para>`、`<item>`、`<description>` 等结构标签行各自成一体，不计入段落长度，否则一份正常的文档会被误报为超标。该判据已固化为本技能目录下的 `scripts/scan-remarks.cs`（C# 单文件应用，需机器上有 .NET 10 SDK），整改与复核一律以它的输出为准（调用时以 `skill_view` 返回的 `skill_dir` 拼接路径：Linux/macOS/WSL 下直接执行 `"<skill_dir>/scripts/scan-remarks.cs" --max 4`，Windows 下 `dotnet run "<skill_dir>/scripts/scan-remarks.cs" -- --max 4`，无超标块时退出码为 `0`；`--help` 会被 dotnet 驱动层截走，取帮助用 `help`），不得口径各异地手工估算。该工具自带 `--self-test`，判据若有改动，改完必须跑它。它只管「段落超行」一条判据；整仓审计的另几类尺子（`scripts/scan-doc-comments.py` 查 summary 多句、中文与内联标签粘连、落款与散文编号、中文里的半角标点）、只改注释的隔离闸门、非 UTF-8 源码的处置、以及审计应遵循的顺序，见 `references/comment-audit-procedure.md`。
-   **列表项与拆句是两回事**：列表化是把若干**各自完整**的论证并排呈现，不是把一句长句按逗号切成多行；每个列表项仍须符合第 1 与第 2 节，即包含逻辑连接的完整句。
-   **豁免范围**：`<summary>` 始终为一句话总述；长度在 1 至 3 行的短 `<remarks>` 无须强加结构；单个无逻辑依赖的事实陈述不受本节约束。
-   **去 AI 腔**：注释与文档只写"依据、事实、后果"三件套，即每个结论都要跟随手册页码或寄存器地址、契约条目、实测结果一类的可核验出处；禁止无依据的评判语与排比套话（如“值得注意的是”“不仅……而且……”）、禁止同义堆叠（如“清晰、明确、简洁”）、禁止结尾升华（如“体现了设计的优雅”），因为这些句子既不承载信息又拉长阅读路径。

#### 3.5 一遍读懂：结论前置、一义一词、一段一主

技术说明被退回的最常见理由不是句子不美，而是读一遍抓不到要点；本节四条与第 1 至 3 节不冲突，它们约束的是**信息排列**，第 1 至 3 节约束的是**句子与结构**。

-   **结论前置**：一段或一节的第一句必须是结论本身，前提、机制、例外一律放在其后。把结论压到第三句之后，读者读完前两句还不知道你要说什么，后面写得多准确都白费。
-   **一段一个主语**：同一句里主语在「作者 / 框架 / 管理器 / 适配器」之间来回切换，读者必须回读才能确定每句在说谁；要换主语就另起一句并把动作主体写全，不要靠上下文暗示。
-   **一义一词，全文只用一个词**：同一件东西在一篇文档里只能有一个称呼。近义词混用（提货单 / 包装 / 产物 / 实例 / 对象）会让读者以为存在多种语义，于是去找它们的差异，找不到就更困惑；做法是首次出现处用一句话定名（如「每次调用给出一份新的 `Lazy<T>` 包装」），此后一律只用这个词。
-   **读者不需要的实现细节不进正文**：写实现的人不需要知道「精确命中时管理器把插件本身当构建器返回、继承链命中时包一层适配器」这类内部分支，除非它改变了他要做的事；把这类细节插在关键结论中间，等于用正确的信息打断论证。

**术语由 owner 拍板，不由写作者自选。** 需要新造或更换术语时，给两个候选、一句话说清取舍让他选（「统一成『提货单』还是『`Lazy<T>` 包装』」），选完就全文只留那一个词；写作者单方面换词，等于让同一批读者在两份文档里学两套叫法，下一份文档又要重新对齐。

**近义词自检：用「在代码里落到哪个表达式」判断是否同义。** 「同一对象」与「同一实例」在 C# 里都落到 `ReferenceEquals`，是同义词，只留一个；真正需要区分的是另两个层次——「包装与产物」（`Lazy<T>` 与 `Lazy.Value` 的返回值）、「同一契约的不同提供方」，这两层各给一个不同的词，不要用同一个词兼指。

#### 4. 标点符号规范
-   中文正文使用全角标点；C# 关键字、类型名、变量名、XML 标签（如 `<see cref="..."/>`、`<c>`、`<paramref name="..."/>`）、字符串字面量（如 `"foo"`）及文档内嵌代码片段或行内标识符均视为代码元素，前后保留半角空格并使用半角标点。
-   并列词语用顿号，并列分句用逗号；当分句内部已含逗号时，分句之间必须用分号分层，避免层级混淆。
-   括号紧贴被修饰词补充说明；引号仅用于特殊含义或字面量字符串，禁止用于普通技术名词强调。

#### 5. 详细度与表达规范（代码注释 + 技术文档）
-   **接口类注释必须详尽**：所有接口及其成员的 XML Doc 须完整阐述契约语义、调用约束、异常行为及实现方需遵守的不变量，不得省略任何可能影响正确实现的上下文信息，其论述按第 3 节分层；契约接口（如服务、驱动抽象）的每个成员 remarks 须写明线程安全要求、异常隔离责任（调用方/实现方/订阅方各自的失败不反噬谁）、生命周期归属（谁创建、谁释放、退订/注销后的语义），这三项是契约实现的隐形雷区，缺一项实现者就会各写各的。
-   **其他类的 public 成员必须有详细注释**：凡 `public` 可见的方法、属性、事件、构造函数等，均须提供包含前置条件、后置保证、副作用及边界情况的完整说明，确保外部调用者无需阅读源码即可安全使用。
-   **XML Doc 标签职责分离**：`<summary>` 仅容纳一句话总述核心功能；契约要点、不变量、设计权衡等复杂论述必须放入 `<remarks>`；前置/后置条件随 `<param>` 与 `<returns>` 就近描述；异常行为专属 `<exception>` 标签；禁止将所有细节堆砌于 `<summary>` 导致信息糊化。
-   **分隔方式按需采用 `#region`**：`#region` 是可读性工具而非格式义务，其价值取决于文件规模与职责数量，因此须按需使用——当文件较长（约 80 行以上）且确含多个可命名的逻辑块（多组方法、接口实现、私有辅助等）时，用 `#region` / `#endregion` 包裹并注明区域名称以助导航；当文件仅数十行、或整个类只承担单一职责时，强行分区反而以形式噪声掩盖了本就一目了然的代码，此时应当不用。判断标准是"分区是否真的帮助了阅读者"，而非"是否套上了格式"。
-   **技术文档论证必须完整（ADR/Plan/Design）**：ADR 的决策理由必须完整呈现背景约束、备选方案与取舍理由，禁止以“决定采用 X”一类单句带过；Plan 的步骤间依赖与前置条件须显式声明，验收标准须可检验；Design 的约束、权衡与边界情况须完整论证，所有论证均须以符合第 1 至 3 节的复合长句表达，并按第 3 节分段与列表化。
-   **ADR 决策修订须带证据链与时间戳**：修订一条已拍板决策（而非新增）时，须在同一文件内记录三件事：原决策及其论据、论据失效的原因（前置条件发生了什么变化）、新决策及其实施依据——禁止只改结论不记失效过程，因为失去失效链的 ADR 会让后来者以为原论据仍成立而据此拒绝新修订。初稿『不做某抽象』的决策在契约落地后失效是典型场景：论据的前置条件消失时结论一并失效。
-   **同一证据链规则适用于 Plan 与 Design 的修订，且修订须就地落地**：改一份已下发的计划文档时，把『前提变了、结论不变（或结论也变）』的说明挂在原先描述那个前提的那一句下面，写成带日期的口径变化条目；禁止只在文末追加『更新：其实……』一段，因为读者按章节顺序阅读时先信了旧前提，文末补丁救不回来。改前提前提之后，凡是与它绑定的量化口径（体量表、批次的工程数与行数、待拍板清单）必须在原位置同步修正，并在原值处留一句『原计 N』，否则同一份文档里会出现两个互相矛盾的数字；同时新增的待拍板项要并入文档自己的待拍板清单，不能只留在对话里，因为下一次接手的人读的是文档而不是聊天记录。
-   **结构化关系优先用 Mermaid 表达**：当文档需要表达流程、时序、状态转换、架构或依赖关系时，必须使用 Mermaid 图（flowchart、sequenceDiagram、stateDiagram、classDiagram、erDiagram、gantt 等）而非文本拼凑的 ASCII 图或表格；表格仅用于真正适合行列对照的数据（如参数清单、评分矩阵、对比表），禁止用表格或文本缩进表达流程与时序等结构化关系。**例外（宿主渲染环境优先）**：面向 gitee 等表格与 mermaid 渲染不稳的平台的开源首页/README，结构图改用仓库内的本地 SVG，表格除「两列三行以内」的对照外一律改为分组列表——图只承载层次，解释写正文，图内不塞图注；此时那一条「必须 Mermaid」不适用，因为渲染坏了比不用图更差。
