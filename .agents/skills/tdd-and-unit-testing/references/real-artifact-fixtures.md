# 用真实产物做夹具

## When to Use

被测代码按文件名、前缀或目录约定去发现并加载真实产物（程序集、配置、可执行文件）时加载本文件。这类逻辑的缺陷集中在「发现」与「坏产物」两端，替身替不掉，得放真家伙。

- **临时目录承载全部产物**：`Path.Combine(Path.GetTempPath(), "前缀-" + Guid.NewGuid().ToString("N"))`；`Dispose` 里 `Directory.Delete(recursive: true)` 并用 `catch (IOException)` 吞掉——清不掉不该判测试失败。不往仓库目录写。
- **测试程序集自身往往就是一份合格产物**：扫描器按前缀发现时，把测试程序集命名到命中前缀（如 `UnitTest.`），用例里 `File.Copy(typeof(夹具类型).Assembly.Location, Path.Combine(appDir, "UnitTest.X.dll"))` 即可充当真产物，不必另建 fixture 工程；同时定义的 public 夹具类型本身就是「会被扫到的东西」。
- **坏产物用确定性字节**：递增字节序列（`0..255`）而不是随机数——「不是合法 PE」这条性质与具体字节无关，随机只会让失败不可复现。
- **非产物样本取自真实依赖**：用构建产物目录里必然存在的、同样命中前缀的某个程序集，并在用例开头用 `File.Exists(...).Should().BeTrue("...")` 断言它存在；否则样本缺失会表现为「扫描一切正常」，测试假绿。
- **断言「只收到该收到的」**：`HaveCount(1)` 加元素标识，而不是 `NotThrow`；坏产物用例则断言「不抛且结果为空」。两者成对，才同时守住发现逻辑与容错逻辑。
- **每个入口各一组用例**：同目录扫描、指定根目录扫描、隔离加载这类多入口，至少各覆盖「命中」与「目录不存在」两种情形。
- **别把 Windows-only 的宿主/Testbed 工程算进本次验证，但也别停在「无法验证」**：`net*-windows` 目标在非 Windows 上会以 NETSDK1100 失败，那是跑错机器、不是改动引起的，不要用 Linux 上的失败去反推自己的改动有问题；同时 Windows 侧有 dotnet，从本会话直接调它把构建、测试、应用启动都跑掉，做法与坑见 `references/windows-runs-from-wsl.md`。把「此项未验证」当交付结论是不合格的——用户会问「你怎么不在 Windows 侧构建」。
- **被测代码自己解析持久化路径时，构造必须能注入路径**：缓存、状态文件、日志这类落位由代码自己算的模块，测试不注入就会被写到开发机真实的用户目录（Windows `%LOCALAPPDATA%`、Linux `~/.local/share`）——用例照样全绿，却在污染真实环境并留下跨次运行的残留。给一个可注入的构造参数（`null` 走生产解析、空串表示禁用、其余直接用），用例一律注入临时路径；跑完再顺手断言真实用户目录没被创建。
- **断言「没被打开 / 没发生」要让夹具本身成为反证，而不是加测试专用计数器**：把「上次判定为非插件」的条目写给一个**内含真插件**的产物——只要它真被打开过，收集结果就必然非空，于是「结果为空」本身即证明文件没被碰过。同类反证还有：手写的状态文件运行后内容一字未变（证明没写）、临时目录里没有残留的 `*.tmp`。计数器是最后手段，且它一出现就该怀疑测试设计。
- **持久化状态文件当夹具：手写一份「上次留下的文件」，用例就同时成了格式契约与失效判据的契约测试**：逐条覆盖写入方身份不符（别的模块/别的库）、部署路径不符、格式版本不符 → 整份忽略并重建（断言条目照常被发现，且文件被重写成当前格式）；判据字段（长度、时间戳）各自单独篡改 → 必须重新扫描。隔离维度每多一个就多一条「不符即忽略」的用例——缺了它，两个写入方互相清空条目这类缺陷会一直绿。
