# TDD 开发模式与单元测试

本技能管两件互相咬合的事：**什么时候写测试**（开发纪律）与**测试怎么写**（单元测试写法）。前一半与语言无关，因为它约束的是顺序与证据；后一半按本仓默认的 .NET 技术栈给出具体口径（xUnit v3 作测试框架、FluentAssertions 作断言、Moq 作测试替身），换栈时只需替换写法那一节，纪律一节不动。这里的 xUnit 一律指 v3 家族（包名 `xunit.v3`，3.x 起），仍在 v2 的项目在动到它时升级，口径见 4.10。

写法那一节里，**断言强度是硬要求而非风格偏好**：单元测试的价值全部押在断言上，断言弱则用例再多也只是把"调用没抛异常"重复了很多遍，因此 4.4 节的强度判据与 4.5 节的禁止写法在评审中按合格线执行，不是加分项。

#### 0. 触发条件与适用范围

加载本技能的场合：新增功能、修 bug、重构、改变既有行为这类需要动生产代码的时候；以及写或改测试文件的时候；用户说 TDD、测试先行、先写测试、加测试、补测试，或指出断言不够严时同样加载；架构师为「某模块无单测」出测试计划并派发补测时同样加载——测试计划本身就是本技能的产物（范围盘点/军规写入 task-desc/批次划分/报告模板），见 4.9。

适用对象是可被单元测试覆盖的生产代码及其测试：纯计算与转换、状态机、协议编解码、映射与投影、边界与错误路径这类不依赖真实外部世界的行为。

不适用的场合见第 6 节；本节先给三条前提：其一，命令一律取本工作群绑定表的 `构建验证命令`，技能正文不写死仓库路径、盘符与测试项目的具体位置；其二，测试框架一律 xUnit v3（包名 `xunit.v3`，本机已见 3.2.2 与 4.0.x 两档），仍在 v2 的项目在动到它时升级并单独提交，升级口径见 4.10；其三，断言方式以所在仓既有约定为准，仓内已有测试换了断言库时跟随仓内，不按本节口径生造第二套。

#### 1. 铁律：没有失败的测试，不写生产代码

先写代码、再补测试的，测试会因为实现已经存在而一次通过，而一次通过的测试证明不了任何事——它可能测错了对象，可能把实现细节当成了行为约定，也可能刚好绕过了没想到的边界。因此铁律是一句话：**生产代码要先有一个失败的测试，而且你要亲眼看它失败**。

判定标志只有一条：你运行过那条测试，看到了它因为「功能还没写」而失败。凡是"我心里清楚它会失败"或者"跑一下肯定红"都算没做。

已经写了代码才发现没测试的，删掉重来。删除的含义是从文件里真的删掉，不留注释掉的残骸、不留在别的分支当参考、也不在执行时"顺手把刚才想好的实现敲进去"——留着就会照着它写测试，那就退回到了测试后补。

#### 2. 红-绿-重构：一步一验

一个循环只推进一步，每一步都带自己的完成标志与验证动作，跳步等同于没做。

**2.1 红——写一个最小的失败测试。** 一次只写一个行为的测试，断言落到可观察的结果上，而不是内部调用了哪个方法。完成标志：测试文件里多了一个测试，除它以外没有动任何生产代码。

**2.2 验红——运行它，看它失败。** 单跑这一条测试按项目的模式三选一：VSTest 模式（项目仍引用 `xunit.runner.visualstudio` 与 `Microsoft.NET.Test.Sdk`）用 `dotnet test <测试项目> --filter FullyQualifiedName~<测试类>.<测试方法>`；Microsoft Testing Platform 模式（.NET 10 SDK 且 `global.json` 指定 `Microsoft.Testing.Platform`，旧 SDK 下则在选项前加 `--`）用 `dotnet test <测试项目> --filter-method <命名空间>.<类>.<方法>`；v3 的测试项目本身就是可执行程序，也可以直接 `dotnet run --project <测试项目> -- -method "<命名空间>.<类>.<方法>"`。在本工作群一律按 `构建验证命令` 的口径执行（WSL 下经 `cmd.exe` 桥接时不要临时拼盘符，按绑定表写法照抄）。在 .NET 10 SDK 上，`dotnet test` 对 xunit v3 项目会直接失败并报 `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later`——SDK 默认走 VSTest，而 v3 只提供 MTP，与项目本身无关（仓内既有 v3 测试项目一律如此，别误判成自己改坏了）。两个可用口径：加 `-p:TestingPlatformDotnetTestSupport=true` 显式选新的 dotnet test 体验；或直接执行产出程序 `dotnet <测试项目>/bin/<配置>/<tfm>/<测试程序集>.dll`——v3 测试项目本身就是可执行程序、自带 in-process runner，摘要行仍是 `Total/Errors/Failed/Skipped`，单跑一条用它自己的 MTP 选项。完成标志有三个，缺一不可：它以失败结束而不是编译错误；失败信息与你的预期一致；失败的原因是"功能缺失"。若它一次就通过，说明测的是既有行为，改测试；若是编译错误，先把编译修好再验红，编译不过的红不算红。改动落在 `net*-windows` / `UseWPF` / `WinExe` 工程上时，「WSL 构建不了所以无法验证」不是可交付的结论：Windows 侧有 dotnet，从本会话直接调它构建、跑测试、起应用都有确定做法（本地化摘要行会让 grep 静默返回空、GUI 应用要用 PowerShell 起、要真实数字就用仓外探针），见 `references/windows-runs-from-wsl.md`。

**2.3 绿——写最少的代码让它通过。** 只写让这个测试转绿所需要的代码，边界、异常、通用化都往后放。允许"作弊"：硬编码返回值、复制粘贴、只处理当前这一个入参，这些都留到重构阶段处理。完成标志：生产代码只增加了让测试通过所必需的部分。

**2.4 验绿——先单跑，再跑全套，再做一次改坏验证。** 先跑刚才那一条测试（与 2.2 同一条命令），确认它通过；再按 `构建验证命令` 跑全套，确认没有把别的测试弄红；最后把实现里与该测试相关的那处判断改坏，确认这条测试变红，再把实现改回。完成标志：目标测试通过、全套通过、输出无新增警告，且改坏验证确实变红——变不红说明断言还不够，回到 4.4 补强。破坏点成组做时（一次破坏多处、跑一次全套），每组先写下**预期变红的用例名**再跑，跑完逐条核对：红得比预期多说明这个破坏点牵连了别的行为、红得少说明有测试没守住它该守的。改完回退后若仍红，先怀疑回退没生效（见上条时间戳陷阱），再怀疑测试。用脚本把实现换回去时**不要用保留时间戳的复制**（Python `shutil.copy2`、`cp -p`、`rsync -t`）：mtime 被还原成旧值后 MSBuild 判定产物仍是最新、跳过重编译，你跑到的还是上一版 DLL，于是"换回去还是红"与"换回去已经绿"两种结论都是假象。用不保留时间戳的复制（`shutil.copyfile`、`cp`），或跑之前强制 `-t:Rebuild`。测试没过就改代码而不要改测试的期望值，除非期望值本身就写错了，这要单独说明理由。

**2.5 重构——只在绿之后做。** 改名、抽方法、去掉重复、把散落的字面量收进工厂方法，全程保持全套为绿，且不新增任何行为。完成标志：全套仍为绿，且改动只涉及结构不涉及行为。重构过程中若测试变红，立刻回退到上一个绿的状态，把步子拆小再试。

**2.6 回到红。** 下一个行为写下一个失败测试；一个循环只加一个行为。

#### 3. 纵向切分：一个行为一个来回

不要先写一堆测试再一起实现。那样做的时候，"红"这一步退化成了"写一堆想象出来的测试"，而测试是在实现还没教会你接口该长什么样之前就定型了，结果通常是又脆又偏——测试盯着你臆想的调用方式，真正该定的边界反倒漏了。

正确的做法是纵向推进：一个行为一个来回，每个来回都让一条端到端的行为从测试穿到实现，前一个来回的结论决定下一个测试怎么写。

```text
错的：红 test1 test2 test3   →   绿 impl1 impl2 impl3
对的：红 test1 → 绿 impl1 → 红 test2 → 绿 impl2 → 红 test3 → 绿 impl3
```

#### 4. 单元测试写法（.NET 默认口径）

**4.1 落位、命名与 DisplayName。** 测试项目沿用所在仓既有命名（本机见过 `<被测>.Tests`、`Tests.<模块>`、`UnitTest.<区域>` 三种，都对，跟仓内保持一致即可），测试文件与被测类型同名、放在同名子目录下，测试类命名为 `<被测类型>Tests`。

测试方法名按顺序编号，写成 `Test001`、`Test002` 的形式，同一测试类内按主题分段：第一段从 `Test001` 起，第二段主题从 `Test101` 起，第三段从 `Test201` 起（Orbit 的既有测试即此写法，便于按主题定位与插入调整）。用途写进 xUnit 的 DisplayName，函数本身不再写 `/// <summary>`：

```csharp
[Fact(DisplayName = "1.最基本的 Xml 解析，有一个正确 Action 节点")]
public void Test001()
{
    // Arrange / Act / Assert 三段照常保留
}
```

DisplayName 的写法要求：一句话说清这条测试守住的校验点，包含输入的关键特征与期望结果，不写"测试17"这类与方法名重复的信息；按主题分段时可用 `3.` 这样的段内序号前缀。测试逻辑较复杂时，函数内部要保留必要的行内注释，用来说明关键步骤、算例来源或容易看错的期望值，但不要为每条测试补一段与方法名同义的注释。

改动既有测试文件时跟随该文件既有风格（本机既有的 `Symbol_Should_Have_Name_And_Location` 加中文 `/// <summary>` 的写法同样合法），同一文件内不混用两种风格；新建文件按本节，但所在测试目录已有成体系的命名风格时（例如整目录都是 `Dispose_Should_Not_Throw` 这类描述性命名加中文 DisplayName），新建文件跟随该目录既有风格，不在同一目录里引入第二套命名。`[Theory]` 场景把编号落在方法名上，DisplayName 写这组数据的共同校验点，每个 `[InlineData]` 的期望值都要可判定。

**4.2 结构：Arrange / Act / Assert。** 每个测试按这三段组织，段间留空行，段落用 `// Arrange` `// Act` `// Assert` 标出；极短的测试允许把 Arrange 与 Act 合成一段并注明 `// Arrange & Act`。`Act` 段只做一次动作，出现两次调用说明这其实是两条测试，拆开。测试内部逻辑加 `#region` 按主题分组，便于按主题单跑。

**4.3 断言方式：一律 FluentAssertions。** 用 `actual.Should().Be(expected)`、`Should().BeEquivalentTo`、`Should().BeEmpty()`、`Should().BeAssignableTo<T>()` 这类写法，同一仓内不要混入 `Assert.Equal` 形成两套风格。集合与对象比对优先用 `BeEquivalentTo`，它的失败信息会指出第一个不匹配的元素，比先 `ToList` 再比字符串更能定位问题。浮点断言带上精度或容差，不写 `Be(0.3)` 这种依赖二进制表示的比较。

**4.4 断言强度：必须能逮住"改坏"。** 单元测试的价值不在用例条数而在断言密度，断言弱的测试即便成百上千，也只是把"调用没抛异常"重复了很多遍。判据只有一条，且要逐条测试执行：**把被测实现里与该测试相关的那处判断改坏（条件取反、去掉边界检查、改默认值、少算一步、把顺序反过来），这条测试必须变红**；改坏之后仍然绿，说明这条测试没有守住任何东西。本节其余规则都是这条判据的推论：

- **禁止单独使用弱断言**：`Should().NotBeNull()`、`Should().BeTrue()`、`Should().BeGreaterThan(0)`、`Should().NotBeEmpty()` 这类存在性断言只能与具体值断言并存，不能作为一条测试的全部断言——它们只回答"有没有"，不回答"对不对"。
- **对象与集合全量比对**：用 `BeEquivalentTo(expected)` 比较整个对象或集合的元素内容，而不是抽查一两个字段，因为未校验字段发生变化正是回归最常见的形式；确有派生字段需要忽略时用 `opts => opts.Excluding(...)` 显式排除，并写明为什么可以忽略。需求要求顺序时加 `WithStrictOrdering()`，只断言元素内容等于放走一类缺陷。
- **字符串与异常消息断言到要点**：`Should().Contain("...")` 要承载真正要守的信息（错误码、字段名、关键片段），能给出完整值时就断言完整值，不用 `NotBeNullOrEmpty()` 代替内容校验。
- **数值、时间与浮点带精度**：浮点用容差（`BeApproximately`）或明确精度，货币与计量带上单位与舍入口径，时间断言校验到需求要求的粒度，不写"不为默认值"这种断言。
- **异常断言三件套**：类型、消息要点、以及相关参数名或内层异常，缺一则无法区分"抛对了异常"与"抛错了异常"：

  ```csharp
  var act = () => parser.Parse("");
  act.Should().Throw<ArgumentOutOfRangeException>()
     .WithMessage("*channels*")
     .WithParameterName("channels");
  ```

  不要用 `try/catch` 加 `Assert.True(false, ...)` 的手法，它会在异常类型不符时掩盖真相；也不要只断言"抛了异常"。
- **状态与副作用双向校验**：既断言调用后应有的变化，也断言不该变化的部分没有变化（未受影响的集合、未变更的标志、未写入的文件），并校验幂等——同一操作执行两遍结果一致。断言「不该发生」时先把这个「没发生」设计成可观察的：让夹具本身成为反证（输入里放一个只有真被处理过才会改变结果的东西），不要为了可观察而加测试专用计数器或去断言日志文本。
- **正反用例成对**：每个"接受"用例配一个同构的"拒绝"用例，即合法输入成功、与它只差一处非法的输入必须给出预期失败；只测 happy path 的测试集在评审时按未完成处理。
- **边界与失败路径逐项对待**：分支（`if`/`else`/`switch` 的每个 case 与默认分支）、边界（0、1、最大、最小、空集合、单元素、重复元素）、非法输入（`null`、空串、越界、类型不符、格式非法）、状态迁移（每个状态至少一次进入与退出）、依赖失败（协作对象返回失败或抛异常时的表现），每一项都要有测试，或写明为什么不需要。
- **一条测试守住一个行为面，但该面的可观察结果要断言完整**：既不要一条测试串起十个不相关断言（失败时定位不清），也不要一条测试只断言一个字段、把它所在行为的其余结果留空。
- **期望值要有来源**：期望值来自需求、手册、算例或独立算出的结果，不从实现里抄；抄来的期望值只会把实现里的错误固化成"正确"。

**4.5 AI 生成测试的典型缺陷（禁止写法）。** AI 生成的测试最常见的失效方式不是写不出来，而是写得很像测试：结构齐全、命名规范、条数不少，但断言只碰到表面，把实现改坏也不会红。以下写法一律禁止，评审发现即退回：

| 缺陷 | 表现 | 纠正 |
|---|---|---|
| 弱断言 | 通篇 `NotBeNull`、`BeTrue`、`Count > 0`，无具体值 | 断言具体值、完整对象或错误消息 |
| 只测 happy path | 没有任何非法输入与失败路径用例 | 按 4.4 的清单补齐正反成对 |
| 断言自己搭的夹具 | 断言替身的返回值、断言 `Setup` 的结果 | 断言被测代码对输入的处理结果 |
| 断言实现细节 | 断言私有成员、断言内部字段、`Verify` 内部协作次数 | 断言可观察行为与对外契约 |
| 无 Act | 只构造再断言，或断言写在 Act 之前 | 每条测试都有一次明确的 Act |
| 雷同用例 | 多条测试只换输入常量，断言完全一样 | 合并为 `[Theory]`，或改断言覆盖不同结果 |
| 覆盖假象 | 用 `[Theory]` 灌一堆数据，断言都是"不抛异常" | 每个 `[InlineData]` 都要有可判定的期望值 |
| 编号即文档 | `Test017` 而 DisplayName 写着"测试17" | DisplayName 写清守住的校验点 |
| 顺序依赖 | 依赖上一条测试留下的状态 | 每条测试独立可单跑，共享状态改工厂方法 |
| 魔数无来源 | 期望值从实现里抄来 | 期望值来自需求或算例，并写出来源 |
| 覆盖报告当结论 | 以行覆盖率高代替断言强度 | 以 4.4 的改坏判据为准，覆盖率只作参考 |

**4.6 测试替身的边界：能不用 Moq 就不用。** 只有跨进程、真实时间、随机数、网络、文件系统、硬件这类不可控的协作对象才需要替身；被测对象自身永远不用替身，用替身包裹被测对象只是在测替身自己的行为。优先顺序是：真实对象（纯逻辑、无副作用）→ 手写 Fake（接口实现简单、需要在测试里积累状态）→ Moq（只需按契约返回固定值或验证调用）。框架里的抽象类型也属于可用 Moq 的一类：`Assembly` 这种类型没法在测试里就地造出"枚举类型时抛异常"的真实对象，`Mock<Assembly>` 是覆盖那条护栏的唯一便宜手段；这类替身要把它会被真实实现先调用的成员（`GetName()`、`FullName`）显式 `Setup`，否则失败会先变成 NullReferenceException，把真正要验的那条路径掩盖掉。用 Moq 时替身按字段声明并在构造处初始化，`Setup` 只搭被测代码真正会走到的路径，`Verify(..., Times.Once)` 只用于调用次数本身就是契约的场景；`It.IsAny<T>()` 用得越多越说明这条测试没在验什么，应当收紧到具体值。

**4.7 时间、随机与并发要变成输入。** 测试里不写 `Thread.Sleep`、不读 `DateTime.Now`、不调无种子的 `Random`——它们让测试变慢且间歇性失败。把时间抽成注入的时钟接口、把随机抽成注入的随机源或显式种子，测试里传入固定实现或固定种子。并发测试用确定性同步点（信号量、屏障、`TaskCompletionSource`）驱动交错，而不是靠 sleep 撞时间窗；并发行为无法确定性复现时，把可复现的那部分逻辑（决策、状态迁移）抽出来做单元测试，把撞时间窗的部分交给压力测试并说明它不属断言型测试。

**4.8 数据构造与隔离。** 常用输入用测试类内私有的工厂方法构造（如 `CreateDriver()`、`CreateSymbol(name: "x")`），避免同一组字面量在几十条测试里重复，改口径时只改一处。测试之间不共享可变状态，静态字段、共享夹具里的可变对象、真实文件与端口都会让测试相互依赖并随机失败；每条测试既要能单独跑通，也要能整类跑通。临时文件用测试专用临时目录并在结束时清理，不往仓库目录里写。

**4.9 补测既有代码（黑盒纪律）与编码注释。**

给**已存在、无测试**的代码补单元测试时，禁止落入「看着实现写测试」的失效模式——实现已经存在，照着方法体写出的断言只是把现状固化成「正确」，实现里的 bug 会被原样固化为期望值。对此用户钦定的四条军规，按合格线执行：

1. **黑盒测签名**：只依据「类型/方法的签名 + XML 文档注释」推导期望值，注释即规格；禁止读方法体来设计用例。文档注释承诺的异常类型、默认值、幂等语义都是可测契约。
2. **期望从严**：全部精确值断言（位值、枚举数值、异常类型与 ParamName、集合逐元素），禁止「返回非空」「大概正确」式软断言；「契约未承诺格式」的字段（如 ToString）只测不抛，不断言具体串。
3. **失败即发现**：跑出失败用例是产出而非事故——保持红、不改实现、不软化断言凑绿；失败逐条记入疑点清单（API 名/输入/期望依据/实测），交决策者拍板修法（修实现或收窄注释）后再动代码。
4. **改坏验证抽样**：交付前对断言强度做抽查——把被测实现的一处判断临时改坏（如比较恒真），对应测试必须变红，验后还原并确认 diff 干净；变不红说明该测试没守住任何东西。

补测时的两个专项处理：TFM 差异导致的特性缺失（如 netstandard2.0 不发射 `IsReadOnlyAttribute`）不是契约违反，改用语义等价断言（IsValueType + IsSealed + init-only setter）并在报告里说明判定调整；internal 类型无 `InternalsVisibleTo` 且禁改 src 时，经反射调用并解包 `TargetInvocationException`，断言不变，后续开了 InternalsVisibleTo 再去掉反射。

补测规模参照：以「每个 public 类型的边界矩阵」为单位规划（空/零/None、极大值、null/空串/空白、重复/幂等、生命周期边界如二次 Start/Dispose 后操作、并发隔离），静态注册表类先 `ResetForTests()` 再断言并用 `[Collection]` 串行；基线既有测试不重写只补缺。

补测并入既有工程后，新增用例可能触发跨类静态互扰：多张测试类各自触碰进程级静态状态（处理器注册表、全局管理器、静态快照）时，串行下全绿、并行调度下必现随机红——逐类补 `[Collection]` 追不完，直接放 `xunit.runner.json` 全工程关并行（parallelizeAssembly=false），以最小代价还原基线；「为并行而重构静态态」超范围不做，等例数涨到串行时长成为瓶颈再立卡把静态态收进夹具隔离。镜像实现（多落地包同名异型）的回归防线用「抽象行为基类 + 各实现派生类只实现 `CreateXxx()`」：同一套行为用例参数化跑每份实现，任一实现行为漂移即精准红在它的参数上。

架构师出测试计划的固定结构（已多次复用定型）：①先盘点被测面并分层——纯数据 record/枚举全部可测，编排与扩展方法用手写 Fake 测，静态生命周期与扫描用测试程序集自带样例类自扫（无 IL 发射），纯 UI 布局不进单测（由宿主实跑冒烟兜底）；②按「纯数据面→编排面→生命周期面→落地包逻辑→HTTP 端点」分批派发，每批一张卡一个主题；③task-desc 必须写全四军规原文＋「禁改 src/（含 InternalsVisibleTo，internal 走反射）」＋「失败保持红记疑点清单」＋弱断言/Sleep/Now 零容忍扫描项；④镜像实现（多落地包同名异型）共用行为测试不重复写；⑤例数估算按「类型数×边界矩阵」给量级即可，不锁死；⑥计划先交用户审定再派发，派发后架构师自审必含改坏验证（临时破坏一处实现验证对应测试变红，还原后 diff 干净）。

疑点红的收口流程（补测批次跑完后）：架构师逐条给出意见（修实现 / 修注释收窄契约 / 期望对齐新契约）交决策者拍板；拍板「改用例期望」时，任务描述里必须写明「替换为另一个精确值强断言，不是软化」——判定标准：新期望与修正后契约逐字一致、断言形式强度不降，即属验收基准随契约更新而非「改测试凑绿」；凑绿特指把强断言换成软断言（精确值改成 NotBeNull 一类），两类改动在 task-desc 里要用这句话显式区分，否则 worker 会把军规「不软化断言」误读为「禁改期望」而卡住。注释放宽契约类收口（如「重复 Map 抛异常」「Id 不做唯一性校验」）不改运行期行为，与其对应的旧断言必然仍红，这两类必须在同一卡里一起处理，不要拆两张卡让红例悬着。

共享工作树上的多会话改动隔离（worker 卡执行期间）：开工前 `git status -s` 快照，发现非本卡的未提交改动（用户或其它会话手改）时用 kanban comment 向 worker 声明「不触碰、不提交、不基于其写测试」，worker 若需干净基线用 `git archive HEAD` 导出纯树验证构建与测试，而不是 checkout 或 stash（会覆盖他人改动）；目标文件恰与手改文件重叠时用 `git add -p` 精准分离，提交后架构师自审要核对该提交 diff 不含他人改动行。

**4.9a 收口批次的结构性拦路：旧断言与新契约方向相反时，必须在同一卡里授权改期望。** 注释放宽契约类收口（如「重复 Map 抛异常」「Id 不做唯一性校验」「吞异常隔离」）不改运行期行为，与其对应的旧断言必然仍红——worker 会卡在「军规禁改断言」与「要求全绿」的矛盾上请求裁定。预防办法：收口卡的 task-desc 在写明「期望对齐新契约」处，同时预先写一句「替换为另一个精确值强断言，不是软化」的授权（判定标准：新期望与修正后契约逐字一致、断言形式强度不降，属验收基准随契约更新而非凑绿；凑绿特指把强断言换成软断言），并强调注释收口与其对应旧断言必须在同一卡里一起处理，不拆两张卡让红例悬着。收口产出的实现类修法在提交说明中引用对应红例编号（T###），使「测试先红→修后绿」的因果链可从 git 历史追溯；报告按「例数/绿红/疑点/纪律执行说明/未覆盖理由」五节固定结构写，疑点未拍板前不阻塞下一批派发（红例悬着是允许状态，拍板后统一收口）。

架构师自审补测批次时，改坏验证的破坏点优先选「匹配/比较逻辑的条件本身」（如把 `A && B` 改恒真、把比较参数开关关掉）而非异常分支——破坏条件逻辑会红掉整组行为用例，能同时验证「断言强度」与「用例分组是否按行为面划分」；破坏异常分支只能验证那一条用例。改坏用 `sed -i` 原地改 + `cp` 备份还原（不保留时间戳，见 2.4），还原后 `git status/diff` 必须核对该文件不在变更列表——还原不干净会把架构师的手改混进 worker 的提交。 新建的测试文件一律 UTF-8。本机部分仓的既有测试文件是 GBK 系编码，读成 UTF-8 会看到乱码，改动这类文件时保持原编码、只改必要行，不要整文件转码——整文件转码会把中文注释变成乱码并把整个文件卷进这次改动，评审时看不出你真正改了什么。测试类上保留中文 `/// <summary>` 说明测什么；测试方法按 4.1 省略函数级注释、由 DisplayName 承载用途，仅在逻辑复杂处保留行内注释；注释写法遵循 `csharp-doc-style`。

**4.10 项目形态与包引用（xUnit v3）。** 新建测试项目一律用 v3 模板 `dotnet new xunit3`（模板开关 `--test-runner [mtp-v2|mtp-v1|vstest]` 默认 `mtp-v2`，`--command-line [xunit|mtp]` 默认 `xunit`），核心包是 `xunit.v3`（需要明确指定时用 `xunit.v3.mtp-v2` 或 `xunit.v3.mtp-off`，`xunit.v3.mtp-v1` 仅存在于 3.x.y）。v3 的测试项目是独立可执行程序，项目文件要有 `OutputType=Exe`，目标框架最低 net8.0；`xunit.runner.visualstudio` 与 `Microsoft.NET.Test.Sdk` 只在 VSTest 模式下需要，为兼容旧版 Test Explorer 可以保留；`xunit.abstractions` 在 v3 已移除，不要引用。

既有 v2 项目（本机 Aegis、Elysium、Umbra 的测试项目现为 `xunit` 2.9.x）在动到它时升级到 v3：包引用换成 `xunit.v3`、加上 `OutputType=Exe`、目标框架提到 net8.0 以上、清掉 `xunit.abstractions`；升级单独提交，不与行为改动或新增测试混在一起，便于出问题时单独回退。v3 的断言库是 v2 2.9 的小超集，升级后可能因新增重载报歧义编译错误，按编译器提示显式指定重载解决，不要退回旧包。

按环境跳过测试用 v3 的 `Assert.Skip`、`Assert.SkipUnless`、`Assert.SkipWhen`（或把 `SkipUnless`、`SkipWhen` 指向测试类上的静态属性），不要用 `#if` 包住测试、也不要删掉当下不适用的测试——跳过会留在报告里，删掉不会。

**4.11 两类需要额外夹具的场景。** 两份只差 logger/命名空间的复制实现（同一逻辑写了两遍、必须一起改）怎么测，见 `references/mirrored-implementation-tests.md`；被测代码按文件名、前缀或目录约定去发现并加载真实产物（程序集、配置、可执行文件）时怎么搭夹具，见 `references/real-artifact-fixtures.md`。

**4.12 测试宿主的进程级初始化。** 被测类型在静态字段初始化期就取进程级门面（日志、配置、容器）时，测试进程必须先完成那次初始化，否则第一条用例就以 `TypeInitializationException` 倒地；而类型初始化失败的缓存是永久的——后来初始化成功也不会让该类型复活。症状极具误导性：整片用例同时红、内层异常写着「某某未初始化」，看着像刚改的代码把功能改坏了，实际是测试进程没有装配宿主。

- 诊断口径：内层异常是门面未初始化、触发点在某个类型的静态字段（`..cctor()`），先去看这门面在**上游库自己的测试工程**里怎么被引导（`tests/` 里 grep `Initialize(`），照抄那个形态，不要自己设计空实现，也不要为此改生产代码。
- 引导写法：测试程序集加 `[ModuleInitializer]` 调一次门面初始化，传空实现（`NullLoggerFactory.Instance` 一类），既不出输出噪声，也不改变生产侧的真实装配。
- 多个测试工程都要时，写一份共享文件，各工程 csproj 用 `<Compile Include="..\Shared\X.cs" Link="X.cs" />` 链进来，不复制正文；同一程序集只能有一个 `[ModuleInitializer]`，而只允许初始化一次的 API 会与「用例自己又初始化一次」相撞，引导只能落在程序集级一次。
- 归因边界：这类红由宿主装配缺失造成，**不是回归**。汇报时把「基线用例数 / 失败数 / 共同内层异常」写清，别让修复者去读业务代码。

#### 5. 常见借口与对应事实

| 借口 | 事实 |
|---|---|
| 「太简单了，不用测」 | 简单的代码照样出错，而这个测试只要几十秒；"简单"通常是因为还没想到边界。 |
| 「先写完再补测试」 | 补出来的测试一次就绿，而一次绿的测试证明不了它测的是需求还是你刚写的实现。 |
| 「我已经手工验过了」 | 手工验过没有记录、不能重跑、下次改动要再来一遍，且覆盖的是你想到的那几条路径。 |
| 「删掉几小时的代码太浪费」 | 已花的时间收不回来，真正浪费的是留着一段没人敢改的代码。 |
| 「TDD 太教条，我这是务实」 | 务实等于早发现问题：TDD 的问题在提交前暴露，绕过它的问题在集成后暴露，后者更慢。 |
| 「留着当参考，测试我另写」 | 留着就一定会照着它写测试，这是测试后补的另一种形式，删了再写。 |
| 「我先探索一下接口」 | 可以探索，但探索产物要丢弃，确定接口后从失败测试重新开始。 |
| 「这条测试很难写」 | 难写通常意味着接口难用，这是设计反馈：先改设计，别改测试标准。 |
| 「用例已经很多了」 | 条数不等于强度：改坏实现仍然全绿，等于一条都没写。 |
| 「断言太具体，改实现就会挂」 | 对外行为不变时测试不该挂；挂了说明它断言了实现细节，把断言改到行为上。 |
| 「覆盖率到了就够了」 | 覆盖率只说明代码被执行过，不说明结果被校验过。 |
| 「换了断言库不是更麻烦」 | 仓内已有测试用什么就跟什么，两套断言并存才是麻烦。 |
| 「等有空再把 xUnit 升到 v3」 | 新建项目用 v3 模板成本为零；既有 v2 项目在动到它时顺手升级并单独提交，拖着才会长期维持两套口径。 |

#### 6. 什么时候不要用它

一次性原型与探索式试验（spike）不写测试，但产物只用于回答"能不能做"，结论写进文档后原型即丢弃，正式实现回到 TDD；生成代码、资源与配置文件、纯 UI 布局微调也不写单元测试，它们分别该由生成器自检、配置校验与人工视觉验证来保证。

单元测试只覆盖单进程内可确定性复现的行为，因此跨进程通信、真实数据库与文件系统、真实网络与硬件、端到端流程、性能与压力这些要交给集成测试、端到端测试与基准测试去验；但这些场景里往往含有纯逻辑部分（报文编解码、状态迁移、重试与退避的决策），那部分仍要按本技能写成单元测试，不要把"这是集成场景"当成整段逻辑不写测试的理由。修 bug 时先写一条能复现该 bug 的失败测试，再修到转绿，这条测试同时充当回归防线。

#### 7. Agent 生成自检清单

提交前逐条核对，勾不上的说明跳过了 TDD：

- [ ] 每条新测试都先运行过、看过它因"功能缺失"而失败，编译错误不计
- [ ] 每个新增或改动的行为都有对应测试，DisplayName 写清了守住的校验点
- [ ] 逐条做过改坏验证：把实现里对应的判断改坏（取反、去掉边界检查、改默认值），这条测试会变红
- [ ] 没有单独出现的弱断言（`NotBeNull`、`BeTrue`、`Count > 0`、`NotBeEmpty` 之类）
- [ ] 对象与集合用全量比对，忽略字段有显式 `Excluding` 与理由，顺序有要求时加了 `WithStrictOrdering()`
- [ ] 异常断言包含类型、消息要点与参数名（或内层异常），没有 `try/catch` 加 `Assert.True(false)` 的写法
- [ ] 状态与副作用双向校验，幂等性有断言
- [ ] 正反用例成对，边界、非法输入、依赖失败逐项有测试或写明不需要
- [ ] 期望值有来源（需求、手册或算例），不是从实现里抄的
