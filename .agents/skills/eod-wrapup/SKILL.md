# 收工收尾

本技能描述一次收工收尾的完整流程：把当天做过的事写成小结并确认落盘，提交一次本地备份，再把计划文档与决策记录的状态更新到与事实一致，使次日开工能凭这份小结直接接续。四步按序执行，顺序本身是流程的一部分。

正文是跨工作群通用流程，双花括号包裹的占位符表示此处取各工作群的绑定值，取值与缺失处理见 `docs/spec/workgroup-binding.md`；正文自身不含仓库路径、看板名、分支名与提交身份。

## 0. 触发条件与适用范围

触发时机：用户说「下班」「下班啦」「做总结」「收工」，或英文 `wrap up`、`end of day`、`EOD`。此时按本文第 2 节的四步执行。

不适用：只做了问答、没有产出可记录的改动时，先说明「今日无需小结」并征得同意，再决定是否跳过；开工那一侧的动作见 `morning-review`。若工作群没有绑定表，先按 `docs/spec/workgroup-binding.md` 落表，再执行本流程。

## 1. 铁律：先落盘，再提交

**先写小结文件 → 确认落盘 → 再提交。** 顺序不可颠倒：即使对话中断，小结已经在磁盘上，不会丢；反过来先提交再写小结，一旦中断就只剩下一条写着 EOD 却没有内容的提交，而**提交信息里的「EOD」不等于小结已落盘**。缺某日小结时，用 `git log --after=<date> --before=<date>` 回溯当天的提交，**核实事实后**补写，不以推测代替记录。

## 2. 流程（按序执行）

### Step 1：写当日小结

小结写入 `{{仓库根}}/{{小结目录}}`，文件名按 `{{小结命名}}` 生成；专题记录可以另起名，但当日小结一律用约定名，不要写成别的形态。小结/计划/决策目录未绑定时，先按约定位置（`docs/daily/<用户名>/`〔旧布局可能写作 `docs/AI-daily/<用户名>/`〕、`docs/plans/<用户名>/`、`docs/adr/<用户名>/`）探测取值并在小结注明「发现值，未绑定」再落笔（发现规则同 morning-review §1）。必须用 `write_file` 真正写入磁盘，**禁止只把内容输出到对话里**。必备章节为完成事项、进行中、阻塞、次日计划、关联文档，完成判据是「次日可凭此文件直接接续工作」；文首的头部表格与本目录既有小结保持一致，并给出分支、起止提交与构建测试基线（`{{构建验证命令}}` 未绑定时注明未采集）。模板见第 3 节。当天中途若已按主题分节写过草稿（边做边记的那种），收工时按本模板**整篇重写**而不是在它上面追加——中途草稿服务于当时汇报，收尾小结服务于次日接续，两者的分节不同。

正文写作遵循 `{{文档规范技能}}`，其中三条对本流程影响最大：引用他人文档必须写出含用户名的完整路径，禁止只写 `ADR-0002` 这类简写；流程、时序、状态与依赖关系用 Mermaid 表达，不用字符拼图；小结正文用复合长句承载逻辑。

### Step 2：确认落盘

`write_file` 之后立刻用 `read_file` 验证文件存在且非空。失败就重试并向用户报错，不得跳过。若发现自己已经说出「小结完成」却没有 `write_file`，停下来补做这一步再往下走。

### Step 3：提交本地备份

```bash
cd {{仓库根}}
BRANCH=$(git branch --show-current)
case "$BRANCH" in
  "{{分支}}"|"{{分支}}"[-/]*) : ;;   # 长期分支本身，或由它派生的特性分支 / 工作群 worktree
  *) echo "当前分支 $BRANCH 不属于 {{分支}} 一族，停止提交"; exit 1 ;;
esac
git status --short               # 只提交本次相关文件，确认没有越界改动
git add -- <显式路径>
git -c user.name="<姓名>" -c user.email="<邮箱>" commit -m "chore: EOD snapshot <YYYY-MM-DD>"
```

- `{{分支}}` 绑的是长期分支名本身（可机器比较），不是描述语句；未绑定时按缺失处理，跳过分支校验并在小结里注明「分支未绑定」。工作群在特性分支或 worktree 上作业时，前缀放行规则让收工提交照常成立。
- `{{提交身份}}` 已绑定时按绑定值显式指定；仓库未配置身份时**必须**显式带 `-c`，否则提交直接失败。

- **只做本地提交，禁止推送**：推送由用户统一执行；也不要为了提交而切换到别的分支。
- 在 WSL 挂载的 Windows 盘（`/mnt/<盘符>/...`）上的仓库里，`git add -A` 可能超时，改用具体路径；**有在途 worker 时绝不可用 `git add -A` / `git add .`**——工作树会被 worker 的写入不断改变，一次全量暂存会把未验收的改动混进收工快照，必须逐个列显式路径（文档路径与任务描述路径分别列出，绑定了 `{{任务描述目录}}` 时任务描述随对应功能提交一并归档）。
- 工作树干净时跳过提交，并在小结里注明「working tree clean, no commit needed」，不要为凑一条提交而提交空内容。
- 提交后在报告里写明在途任务的 id、assignee 与断点，供次日接续。

### Step 4：更新计划与决策状态

1. 在 `{{仓库根}}/{{计划目录}}` 下读出当天相关的 `PLAN-<四位>-<slug>.md`（退役的到 `archive/`、`deprecated/` 里找）。
2. **就地编辑，不是新建文件**：逐项更新状态标记，并在文末追加当日日期与进度摘要。
3. 计划全部交付后按 `{{归档约定}}` 退役；**归档不是只搬文件**——只把文件移进归档目录而不更新其中的清单、评审表与完成头，等于留下了一份自相矛盾的文档，判为不合格。移入时保留原有标识，并在文首补退役登记块。
4. 当天若有结论改动了契约或架构，确认已落 `{{仓库根}}/{{决策目录}}/ADR-<四位>-<slug>.md`；状态仍是 `Proposed` 的列入次日待拍板，**未拍板的调研结论不得当作决策引用**。
5. 既无活跃计划也无新决策时，在小结里明确注明「无活跃计划 / 无新决策」，不能什么都不说直接跳过。
6. 未绑定计划目录或决策目录的工作群，跳过对应子步骤并在小结中注明。

## 3. 当日小结模板

```markdown
# {日期} 工作小结

| 项目 | 内容 |
| :--- | :--- |
| 日期 | {YYYY-MM-DD} |
| 记录人 | {用户名} |
| 当日主线 | {一句话概括} |
| 基准 | 分支 `{{分支}}`，起点提交 `{hash}`，业务提交终点 `{hash}`（本次收尾快照自身的 hash 不写进来）；build {N} 警告 {N} 错误、test {N} 项{通过/失败} |

## 完成事项

（按主题分小节；写清任务编号、复核结论与提交 hash）

## 进行中

（每项写清当前断点与后续步骤）

## 阻塞

（写清阻塞类型：缺决策 / 缺信息 / 契约冲突；缺决策的指名是哪份决策记录）

## 次日计划

（按优先级排序，每条可检验）

## 关联文档

（逐条写含用户名的完整路径）

## 遗留与说明

（不代为补写的缺口、当日发现但未处理的问题）
```

## 4. 常见陷阱

1. **漏写小结**：提交不能替代当日小结；缺日文件用 `git log` 回溯核实后补写。补写不是重写历史，三件事固定：① 文首注明补写日期与依据（提交、分析文档、计划进度记录）；② 当日被后续事实推翻的判断**保留原样**，另开「事后补记」节说明，不改当时的记录；③ 当日没有提交也没有文档留痕的活动如实写「无留痕」，不把推测写成事实；项数基线若是转引自计划记录，标注「取自计划记录，未重跑」。
2. **写在错误的分支上**：共用检出里别的会话随时会切分支，**把分支名抄在眼前看是不够的**——检查与提交之间仍会被切走。门禁必须与提交在同一条命令里，用 `[ "$(git branch --show-current)" = "{{分支}}" ] || exit 1` 卡住，先 `git add --` 显式路径再 `commit`。已经落到错分支上的补救：`git branch -f {{分支}} <该提交>`（目标分支未在别处 checkout 时是快进，安全）→ `git checkout {{分支}}` → `git branch -D <错分支>` → `git show --stat HEAD` 核对内容；不要用 revert / cherry-pick 绕，那会留下两条同内容的提交，且错分支仍在。
3. **误推送**：本流程只做本地备份，推送由用户统一执行。
4. **把看板开关当命令**：`boards switch` 是假开关，看板一律用 `--board` 或环境变量指定。
5. **文件名不合约定**：当日小结必须按 `{{小结命名}}` 生成，不要临时发明第三种写法。
6. **文档引用写简写**：`ADR-0002` 这类简写在多目录多人协作下无法解析，必须写含用户名的完整路径。
7. **收工时仍有在途 worker**：此时必须逐个列显式路径暂存，禁用 `git add -A`，否则未验收的改动会混进快照。
8. **在途任务的改动判定按当下事实写**：worker 可能整段时间只在读代码而未落盘，小结里不要写「改动尚在工作树中」，改为「改动当日不提交，将在工作树中累积」，以免与实际不符。
9. **归档只搬文件**：移动计划或文档时不同步更新正文里的状态与完成头，等于制造两份互相矛盾的记录。
10. **把未拍板的结论当决策**：状态为 `Proposed` 的结论只能列入次日待拍板，不得作为派发依据。同理，**计划文档里的技术方案被当日侦察推翻时**（如「转换扩展落基础库」实测发现撞发包门、本地 20 行即可），在任务书里按实测修正并在交付汇报单列计划偏差——静默偏离计划会让下次开工的人把过时方案当既定事实。
11. **别在本次提交的内容里写本次提交自己的 hash**：`git commit --amend`（以及任何再改动）都会换掉 hash，被引用那句话立刻自相矛盾，而你只能靠再改一次内容去追它。小结的「基准」行写起点与**业务提交**终点即可，收尾快照本身用「本文件随其后的收尾快照提交入库」这类说法指代；确需精确 hash 处（例如要给别人引用），在提交完成之后另行记录。
12. **远端状态必须联网实测，本地 `origin/` 引用不作数**：共用检出时别的会话可能就在你写小结这几分钟里把它推上去了（或推走了别的分支），而**别人推的不会更新你本地的 `origin/<分支>`**——本地引用与 `HEAD` 相等既可能是真已推，也可能只是自己最后一那次 push 留下的旧快照，两种情形靠 `git log origin/<分支>..HEAD` 分不出来。落笔前跑一次 `git ls-remote origin <ref>` 拿服务端真值，再写「哪些提交已推、哪些未推」；要写 hash 就写刚读到的那个，并注明推送是否由本会话执行。
13. **`git add` 的路径表里只要有一条不存在，整条命令中止、什么都不暂存**：把 `-A` 与显式路径混写（`git add -A <文件> <另一个刚被删除的文件>`）时，不存在的那条会让整条命令失败，若还把 stderr 折进 `/dev/null`，这次失败就会被读成成功——于是收到一条只含部分改动的收尾快照（典型症状：提交里只有那一处删除，其余改动全留在工作树）。规矩：要全量就单用 `git add -A`，要精确就 `git add -- <存在且确要的路径>`，两者别混写；并且不凭 `git commit` 的成功输出判断内容齐了，提交后一律用 `git show --stat HEAD` 核对文件表，缺项在未推送时 `git commit --amend` 补齐。

## 5. 自检清单

收尾完成前逐条核对：

- [ ] 小结已用 `write_file` 落盘，并用 `read_file` 确认存在且非空
- [ ] 文件名符合 `{{小结命名}}`，位置在 `{{小结目录}}` 之下
- [ ] 小结含完成事项、进行中、阻塞、次日计划、关联文档五节，且次日可凭它接续
- [ ] 引用他人文档处写的是含用户名的完整路径，没有简写
- [ ] 提交前核对了分支，提交只含本次相关文件（并在提交后用 `git show --stat HEAD` 核对过实际吃进的文件），测试与构建基线已记入小结
- [ ] 小结没有引用本次收尾提交自己的 hash；push 状态是按提交前那一刻重读的远端 ref 写的
- [ ] 没有推送，也没有为使工作树干净而丢弃他人改动
- [ ] 有在途 worker 时，暂存用的是逐个显式路径而非 `git add -A`
- [ ] 计划文档是就地更新而非新建，交付完毕的已按 `{{归档约定}}` 退役并同步了正文状态
- [ ] 状态为 `Proposed` 的决策已列入次日待拍板，未被当作结论引用
- [ ] 无活跃计划或无新决策时已明确注明，而不是留空跳过
