# 项目接入与技能同步（Agent Project Rollout）

本技能管一件事：**把一个项目的 agent 接入面接上并保持同步**——技能副本、根路由表、外部技能、以及项目同时是工作群时的 profile 接线。它不写技能正文（那是技能文档规范的事），不定文档目录与命名（那是文档脚手架技能的事），也不是随手可用的工具：它是**维护告一段落之后的那一次全量铺开**（见第 8 节）。

#### 0. 触发条件与适用范围

加载场合：用户说「给这个项目接入 agent」「部署同步」「技能同步到项目」「项目体检」「盘点技能副本」「把技能铺开」；某个项目要开始用本仓的技能；同事拿到本仓后要在自己机器上接第一遍（本机接入）；或一轮技能维护结束、要往各目标落盘。

适用对象：任何需要本仓技能的项目仓库（无论是否同时是 Hermes 工作群），以及本机 Hermes 的技能根与各 profile 的技能目录。

不适用：技能正文怎么写、frontmatter 怎么填（技能文档规范管）；项目 `docs/` 目录与文档规则的建立（文档脚手架技能管，本技能只在第 3 节第 6 步调用它并按它的清单验收）；技能本身要不要新增或修订（那是维护期的事，维护中途不做部署，见第 8 节）。

#### 1. 两场景与共用骨架

两个场景的差别只在入口，判据、核验与报告口径完全一致：

- **场景一 新建项目接入**：项目还没有技能根，从零建立接入面，入口是「建」（第 3 节）。
- **场景二 已有项目体检与同步**：项目已经在用，可能有落后的副本、被本地改过的副本、旧实现残留与过期声明，入口是「查」，按差异分类处置（第 4 节）。

场景一做完之后项目就进入场景二的状态，此后长期走场景二。

共用骨架六步，每一步的产物都是下一步的输入：

```text
盘点（只读）→ 计划（预演）→ 落盘 → 核验 → 提交 → 报告
```

#### 2. 三件前置事实

**唯一真源。** 本仓是技能的唯一真源，技能位于本仓 `skills/<技能名>/`，改动只在这里发生；项目仓库里与 Hermes 技能根里的同名目录一律是下游拷贝、只读。由外部维护的技能例外：正文不进本仓，只在本仓 `docs/spec/external-skills.md` 登记上游坐标（仓库、许可证、钉住的完整提交号、上游路径），分发走外部分发工具。

**副本只读、行尾 LF。** 要改就改真源，副本只被覆盖；副本行尾一律 LF——同一份内容在两种行尾下哈希不同，会让「内容一致」被判成差异，也让 Windows 侧长期挂着一堆无关的改动。

**三种落地约定并存，但对 Hermes 只有两种生效。** 项目侧的技能根有三种约定：`.agents/skills/`、`.ai/skills/`、`.dsh/skills/`（技能目录都长成 `<技能根>/<技能名>/SKILL.md`），而 Hermes 认的项目技能根只有 `.agents/skills/` 与 `.hermes/skills/` 两个（依据是它的 `agent/skill_utils.py` 里 `PROJECT_SKILLS_SUBDIRS` 的定义），放进 `.ai/skills/` 或 `.dsh/skills/` 的技能它既不加载也不提示。因此新建项目按「会不会被 Hermes 直接读取」定：要接 Hermes 的建 `.agents/skills/`，只给项目团队与其它工具读的建 `.ai/skills/`；已有项目沿用它自己已经在用的那一种、不主动更换，换约定会让既有的加载路径失效，若那一种不是 `.agents/skills/` 又希望 Hermes 读到，按第 6 节把该目录写进 profile 的 `skills.external_dirs`。技能正文引用自己的脚本一律相对技能目录，不写死这三种前缀。

#### 3. 场景一：新建项目接入

1. **定技能根。** 先看项目里已经有哪种约定（`.agents/skills/`、`.ai/skills/`、`.dsh/skills/`），有就沿用；都没有则按上一节的判据选：要接 Hermes 的建 `.agents/skills/`，只给项目团队与其它工具读的建 `.ai/skills/`（放进 `.ai/skills/` 又想被 Hermes 读到，必须另把它写进 profile 的 `skills.external_dirs`，那时它是优先级最低的外部档而不是项目档）。完成标志：路径存在，且在本项目会被读取的位置上（项目同时是工作群时，profile 侧的技能根另按第 6 节接线）。
2. **登记目标。** 把该技能根路径加进本机目标清单（每行一个目录，`#` 开头为注释；例如 `~/.hermes/youren-targets.txt`；清单是本机事实、不进仓，可以另存多份对应不同批次）。完成标志：清单里能查到该路径，且路径是绝对路径。
3. **落技能。** 先 `tools/sync-skills.cs --dry-run --targets-file <清单>` 看逐目标明细（该目标下每个技能应显示为「新增」），确认待处理项与预期一致，再去掉 `--dry-run` 落盘。完成标志：落盘退出码 0，且再跑一次 `--dry-run` 归零。
4. **落外部技能（项目需要时）。** 先 `tools/fetch-external.cs --list` 看登记表有哪些外部技能，再 `tools/fetch-external.cs --install --fetch --latest --targets-file <清单>` 预演（退 3 表示有待处理项，属正常）；`--latest` 会先联网把登记表的 `钉住提交` 更新为上游 HEAD，实现「每次部署取最新」，确认待处理项后加 `--apply` 落盘，最后 `--verify` 核到退 0。完成标志：`--verify` 退 0，核对记录已追加本次取到的提交号。
5. **写根路由表。** 在项目根的 `AGENTS.md` 里起一节「按需技能」，逐条写「技能名 → 何时加载 → 路径」，路径按第 1 步定下的那一种约定写成 `<技能根>/<技能名>/SKILL.md`，不写死其它两种；同一节里写明权威源：**技能正文以本仓为准，本目录是下游拷贝，冲突以本仓为准**。完成标志：已落盘的每个技能都有一条，且表格里的路径指向真实存在的文件。
6. **建文档体系。** 按文档脚手架技能落地 `docs/` 目录与规则，本技能只负责调用它并按它的自检清单验收，不代管文档规则本身。完成标志：文档脚手架技能的自检通过。
7. **工作群接线（仅当该项目同时是 Hermes 工作群）。** 按第 6 节逐条做：全 profile 走 external_dirs 指向本机克隆、清掉本地同名副本、绑定表、trust 与索引核验。完成标志：该 profile 的技能指纹快照里能看到落下的技能名，且它的绑定表齐备。
8. **首次提交与报告。** 按第 7 节各仓独立提交，报告只进会话。完成标志：该仓提交后工作区干净，会话报告里给出每目标的新增数与核验结论。

#### 4. 场景二：已有项目体检与同步

1. **盘点（只读，不动任何文件）。** 五件事各有输出，且每条结论都要能贴出证据（路径、哈希、标题行），不写「应该没问题」这类无法复核的话：
   - **副本清单**：该项目一共有哪几处技能根（仓库根一处、子项目还可能各有一处），逐处列出技能目录。
   - **版本桶**：按内容哈希分组得出「与真源一致 / 落后于真源 / 被本地改过」三桶；比对前先把行尾归一，CRLF 与 LF 的内容是同一份，不归一会把行尾差误判成内容差。
   - **残留**：真源里已经删掉的技能目录、被 C# 实现取代的旧脚本（如遗留的 `.sh`、`.py`）。
   - **接入面**：根路由表是否登记了全部技能、路径是否指向真实文件、是否写着权威源是本仓。
   - **目标清单**：这几处技能根是否都在本机清单里；不在的就是「没人管的副本」，最容易长期漂移并最终与真源分叉。
2. **计划（预演）。** `tools/sync-skills.cs --dry-run --targets-file <清单>`（必要时加 `--report-extra` 把「目标里多余、真源没有的技能」一并列出）；外部技能先 `--verify`。完成标志：拿到逐目标的「新增 / 更新 / 一致」明细与合计处数。
3. **差异分类与处置。** 每一处差异归到下表某一类并写下动作，不按感觉统一覆盖：

   | 类别 | 判据 | 处置 |
   | :--- | :--- | :--- |
   | 真源已更新 | 副本内容落后于真源 | 覆盖（落盘即完成） |
   | 副本被本地改过 | 该副本与真源、与同项目其它副本都不一致，而真源侧没有对应改动 | 先把有价值的改动搬回真源（维护期做的事），再用真源覆盖；无价值则直接覆盖 |
   | 多余残留 | 目标里有真源已没有的技能目录或旧实现文件 | 删除；这是本技能里唯一允许的删除动作，删前确认没有别的目标或文档在引用它 |
   | 仅行尾不同 | 归一化后内容一致 | 用同步器统一为 LF，不手工改副本 |
   | 接入面过期 | 路由表漏登记技能、路径写死成别的约定、文档里的权威源指向旧位置 | 改这几处文档，使它们指向本仓 |

4. **落盘与核验。** 落盘后重跑 `--dry-run`（应归零）；外部技能 `--verify`（应退 0）。完成标志：两个命令的结论都是「无待处理」。
5. **提交。** 按第 7 节各仓独立、范围限定地提交。完成标志：各仓提交后工作区干净，且各仓同一文件的 blob sha 一致。
6. **报告。** 只进会话：逐目标的新增 / 更新 / 跳过数、核验结论、各仓提交状态与未提交项，以及仍需用户定夺的项（例如要不要把某处本地改动搬回真源）。

#### 5. 两个分发工具的对外契约

两者都是本仓自带的 C# 单文件应用（.NET 10 SDK）：Linux / macOS / WSL 下直接执行 `tools/<工具>.cs 参数`（需执行位），Windows 下 `dotnet run tools/<工具>.cs -- 参数`；直接执行时 `-h`/`--help` 会被 dotnet 驱动层截走，取帮助用 `help` 或 `-?`；改动工具之后先跑 `--self-test`。

- **`tools/sync-skills.cs`**——本仓 `skills/` → 目标技能目录的单向同步。开关：`--dry-run`（只报不落盘）、`--skills a,b`（限定技能）、`--report-extra`（连目标里多余技能一并列出）、`--targets-file F`、`--self-test`。方向永远是「本仓 → 目标」，目标侧的改动会被覆盖；退出码 0/1/2 依次为「完成或一致 / 参数或环境错误 / 同步后校验失败」。
- **`tools/fetch-external.cs`**——上游仓库 → 目标技能目录的外部技能分发与核对。开关：`--list`、`--verify`（不带动作时的默认）、`--install [--apply]`（不带 `--apply` 只预演）、`--fetch`（先更新上游缓存，首次与跟随更新时都要加）、`--latest`（把登记表的钉住提交更新为上游默认分支 HEAD 并回写登记表，实现每次部署取最新；不给目标时只回写 pin）、`--skills a,b`、`--targets-file F`、`--registry P`、`--cache D`、`--self-test`。退出码 0/1/2/3 依次为「一致或已完成 / 参数或环境错误 / 落盘后校验失败 / 发现差异或存在待处理项」；预演与核对在有差异时退 3，据此判断该不该落盘。

工具只是加速器：第 3、4 节的每一步都能不靠工具做完（手工比对、手工复制、手工提交），工具的作用是省事与保证幂等，因此工具跑不了时按人工步骤继续，不要卡住。

#### 6. Hermes 环境下的接线

项目同时是 Hermes 工作群时，除项目侧技能根之外还要接线；下面每条都是实测过的坑，按顺序做：

- **Hermes 侧不再复制技能，改走 `skills.external_dirs` 指向本机一份克隆。** 在 profile 的配置文件（`~/.hermes/profiles/<profile>/config.yaml`，default 是 `~/.hermes/config.yaml`）的 `skills:` 段加一条 `external_dirs: [~/.hermes/youren/skills]`，指向本机原生文件系统上的一份本仓克隆（例如 `~/.hermes/youren`，用 `git clone` 得到）；外部目录由 Hermes 只读使用，创建技能永远写本地技能根，同名时**本地技能压住外部技能**。更新＝`git -C ~/.hermes/youren pull --ff-only`，新增技能不必再碰任何 profile。
- **为什么用本机克隆，而不是直接指向真源。** 直接指挂载盘上的真源，会让每次会话构建都依赖该盘在线，且可能读到正在编辑中的工作副本；放在原生文件系统上的克隆与盘是否挂载无关，只在显式更新时才需要源。克隆只拉不推，改动一律在真源做，两端不会各改一半。
- **本地同名副本必须清干净，否则外部版本永远不生效。** `~/.hermes/profiles/<profile>/skills/<技能名>`（软链或实体目录）与 `~/.hermes/skills/<技能名>` 只要还在，就会静默压住外部版本，表现为「改了真源却不见变化」；接线时逐 profile 清掉并在核验里复查。删软链用 `rm -f`，路径**别带尾斜杠**（`rm -rf link/` 会顺着链删掉目标内容）。
- **判「有没有装上」要问加载器，不看文件在不在。** 硬证据是让加载器自己回答：列出该 profile 解析到的技能根与技能名（`get_all_skills_dirs()` 与 `iter_skill_index_files()`），或退一步用 `hermes -p <profile> skills list --source all`——注意那张表的列宽会截断长技能名，匹配时要按前缀，按全名匹配会漏。每个 profile 构建提示词时还会写下 `.skills_prompt_snapshot.json`，技能名出现在里面才算真的被加载；改完接线要新开一次会话或跑一次非交互会话才是新状态。要单独确认项目档的状态，问加载器的另外两个入口：`get_project_skills_dirs()` 返回当前工作目录所属仓库里被 trust 的项目技能根，`get_untrusted_project_skills_root()` 返回未 trust 的仓库与被搁置的技能数——横幅那句提示就是后者给的。
- **搜索类工具不跟随软链。** 若某处技能根仍是软链形态，ripgrep 系会把软链技能整个漏掉，`find -L <技能根> -maxdepth 2 -name SKILL.md` 才看得全。
- **克隆出来的新 profile 会「假安装」插件型技能。** `hermes profile create --clone-from` 会带走配置里的插件启用清单，但不带插件目录，于是插件写着启用却根本没加载；判据是配置里有名字而对应目录不存在，修法是从任一在用 profile 复制副本再启用（不要重跑插件安装，会被技能扫描器拦）。
- **项目副本要不要生效，先定口径再动手，别照着提示点。** Hermes 读到的技能分三档，优先级从高到低是项目档（`.agents/skills/` 与 `.hermes/skills/`，仅当仓库根在该 profile 的 `skills.trusted_project_dirs` 里、且会话工作目录解析到该仓库时才参与）、本地档（`~/.hermes/skills/`）、外部档（`skills.external_dirs`，本仓克隆走的就是这一档）；同名技能只留优先级最高的那一份，项目档先入并把被它压住的本地条目丢掉，外部档最后入且跳过已经出现过的名字。两种做法互斥，接入时选定一种写进本项目的接入说明：**真源唯一模式（推荐）**——项目副本只服务项目团队与其它工具，Hermes 侧一律不 trust，并给工作目录会落在该仓库的 profile 设 `skills.project_discovery: false`；**项目副本模式**——`hermes skills trust <仓库根>`（per-profile 设置，反向用 `hermes skills untrust`）让副本成为最高优先级的加载源，代价是它静默压住克隆里的同名技能、副本必须随每轮铺开同步，且每次 `git pull` 进来的内容都要重新过一遍 Hermes 的 skills_guard 扫描，被判为危险的技能会被静默隔离、不进索引。
- **横幅提示按上一条的口径处置。** 会话里出现「◆ N project skill(s) found in <仓库> but not loaded — run `hermes skills trust` to enable them.」，说明工作目录落在该仓库、仓库里有项目技能根、而仓库根未 trust；真源唯一模式下正确的处置是给相关 profile 设 `skills.project_discovery: false`（配置一律用 `hermes config set` 写，不手改配置文件），而不是照提示去 trust——照做就会让那份可能已经过期的副本压住真源，等于把真源又弄丢一次。
- **绑定表先于技能。** 技能正文里的 `{{占位符}}` 取值来自该 profile 的 `SOUL.md` 中「工作群绑定表」一节；新增工作群先落绑定表再加载技能，没有绑定表等于拿别的工作群的值干活。
- **收尾体检。** 若项目用了插件型技能，新增或同步后对其相关 profile 逐个跑一次插件体检（`hermes -p <profile> plugins doctor <插件名>`）确认注册正常。

#### 6b. 工作群角色定义（`.agents/user-profile/<用户名>/`：根 `AGENTS.md` 只做路由）

用户要求「角色配置参考某仓的做法 / root 只做导流 / 去个人档案里找各子 agent 的角色定义」时走这一节。产出的是**能被 agent 直接照着干活的口径**，不是把名单堆回根文件。

1. **先读参照仓的实际形态，别凭印象造**：根 `AGENTS.md` 只保留项目/目录/构建测试/文档入口 + 一段「按角色路由」的定位步骤；个人档案根固定为 `.agents/user-profile/<用户名>/`，入口是同目录 `README.md`，项目组、岗位与看板信息在同目录 `team-info.md`，个人约定在 `conventions.md`，逐岗位细则在 `roles/<岗位>.md`，跨岗位共用约定在 `shared/`。`docs/agentSet/` 已废止，不再作为角色或名单的落点；遇到旧目录只按迁移规则处理，不在其中新增文件。用户名取 `git config user.name`；仓库 git 名与目录名不一致时（本机 git 名是 `Erian Lu`、目录名写 `lukan/`）在 `README.md` 或 `team-info.md` 的信息表里显式写出两者对应。
2. **角色正文从个人档案提取，不发明域**：可写范围逐目录列（含测试工程清单、嵌套多一层的工程路径这类只有 `README.md` 才有的细节）、禁碰逐项列（他人档案、仓库根、`docs/` 他人目录、只读子模块）、构建与测试命令抄成可直接粘贴的形式、结尾单列「交卷」要求。运行时会话仍以 Hermes profile 的 `SOUL.md` 为准，仓内派发与验收口径以 `.agents/user-profile/<用户名>/` 为准；两者冲突时先改仓内档案对齐 `SOUL.md`，不要另建 `docs/agentSet/` 形成第三套话。
3. **根 `AGENTS.md` 换成路由**：取 `git config user.name` → 读 `.agents/user-profile/<用户名>/README.md` → 目录不存在就按其自身环境工作、不套别人名单 → `.agents/user-profile/<用户名>/` 与 `docs/<类型>/<用户名>/` 之外只读、个人档案由主人维护 → 现行登记清单。同时把 `.agents/user-profile/` 补进目录表，技能表（技能名 → 何时加载）留在根文件；`.agents/<域>/<用户名>/`（`roles/`、`rules/`、`tasks/`、`team/`、`wiki/` 等）不再新增。
4. **同仓多个工作群时只登记被点名的那一个**，另一个显式写「暂以各 profile 的 `SOUL.md` 为准、未登记」，不要顺手替它编名单。
5. **角色文档里点名技能前先确认它真的入库**：点到真源里没有的技能名，等于给下一轮埋空指针（本机 `user-facing-copy` 就只在两个 profile 本地存在、游刃里没有）。要么把口径写成句子，要么先把它收进真源。
6. **提交与边界**：按第 7 节，工作群仓可提交不推送；`.agents/user-profile/<用户名>/` 归该用户维护，agent 改它必须由用户点名，改完在报告里列出新增文件名与全文校验结论；不再把 `docs/agentSet/` 当作个人或团队配置目录。

#### 7. 提交与报告

- **各仓独立提交**：每个目标仓库在自己的仓里提交本次落下的副本，不跨仓拼一个提交。
- **范围圈死**：`git add -A -- <技能根目录>` 与 `git commit -- <技能根目录>` 都带路径限定，提交前先看 `git diff --cached --stat`，确认没有把别人的文件、或上一次失败提交留在索引里的文件混进来（本仓规矩：一次提交只做一件事，混了就 `git reset --soft HEAD~1` 加 `git restore --staged <文件>` 再分两次提交）。
- **身份**：仓库里已配 `user.name`/`user.email` 的沿用；没配的不要往仓库配置里写，用 `git -c user.name=... -c user.email=...` 临时指定。
- **提交后自证**：`git -C <仓库> rev-parse HEAD:<技能根>/<技能名>/SKILL.md` 在各仓应得到同一个 blob sha，一次证明各仓提交的是逐字节同一份内容；仓库若打「LF will be replaced by CRLF」告警属正常，索引里仍是 LF。
- **提交即止**：工作群分支的约定是「可提交、禁止推送」，推送与合并请求由用户统一处理，要不要推要问。
- **报告只进会话、不落盘**：给出逐目标明细（新增 / 更新 / 跳过）、核验结论（`--dry-run` 归零、`--verify` 退 0）、各仓提交状态与 blob 一致性，以及仍需用户定夺的项。不要把它写成仓库里的部署文档。

#### 8. 部署时序：维护期不铺

本技能是**维护告一段落之后的那一次全量铺开**，不是随时可用的随手动作。维护期（技能正在连续新增与修订时）只改本仓、只报待处理处数（`--dry-run` 的合计与逐目标明细），不往任何目标落盘：每改一次就铺一次，会让多个目标根反复变脏，每个下游仓再各提一次没人会读的提交。等用户说维护告一段落，再按第 3 节或第 4 节一次性铺开并各自提交；外部技能的铺开同样等这个时点。

#### 9. 常见错误与处置

| 现象 | 原因 | 处置 |
| :--- | :--- | :--- |
| 预演显示副本「更新」，但你确信没人改过 | 只是行尾不同 | 归一化后比对确认，按工具统一为 LF |
| 改了真源，Hermes 侧没变 | 本地还有同名副本压住外部版本（profile 的软链或实体、`~/.hermes/skills/` 里的旧副本）；或克隆没更新 | 清掉本地同名副本、更新克隆（`pull --ff-only`），按第 6 节核验 |
| 改了真源，项目侧副本没变 | 没跑同步器 | 按第 4 节同步并提交，改动不要直接落在副本上 |
| profile 里看不到新技能 | 会话未重建，指纹快照还是旧的 | 新开一次会话或跑一次非交互会话再看 |
| 目标仓出现大量改动且只有行尾不同 | 行尾自动转换与 LF 口径的交互 | 用忽略行尾的方式比对，确认内容一致后再决定要不要提交 |
| 挂载盘上的仓报索引锁 | 另一侧还有 git 进程在跑（WSL 侧的 `ps` 看不到 Windows 侧的 `git.exe`） | 用 `tasklist.exe /FI "IMAGENAME eq git.exe"` 复核；两边都无进程、锁文件为 0 字节且 mtime 已过数分钟，才判为残件并删除，否则等 |
| 全盘扫描像卡住、不报错 | 挂载盘不是原生文件系统（WSL 的 9p、网络盘），递归搜索单次可到数百秒 | 加 `-maxdepth`、优先走索引（`git ls-files` / `git grep`）、或把内容先落到 ext4 侧；不要把全盘扫描塞进有超时的批处理里 |
| 提交里混进了不属于本次的文件 | 上一次失败的提交把文件留在索引里 | 提交前看 `git diff --cached --stat`；混了就软回退一步、取消暂存该文件，再分两次提交 |
| 新克隆的工作群「装了技能却用不上」 | 工作目录不在仓库内、技能只落在仓库副本没进 profile 技能根、或本地同名副本压住了外部档 | 按第 6 节逐条核对：external_dirs 指向的克隆 → 无本地同名副本 → 加载器能列出技能名；项目副本口径按选定的一种执行到位 |
| 会话每次启动都提示「N project skill(s) found in <仓库> but not loaded」 | 工作目录落在该仓库、仓库有项目技能根、仓库根未 trust，而该 profile 的 `skills.project_discovery` 未关 | 按第 6 节选定的口径处置：真源唯一模式下设 `skills.project_discovery: false`，不要照提示去 trust |
| 照提示 trust 之后，改了真源反而看不到变化 | 项目档优先级高于外部档，仓库里那份旧副本静默压住了克隆 | `hermes skills untrust <仓库根>` 回到真源唯一模式，或把那处副本同步到最新（此后副本即实际真源），二者择一 |
| 技能放进了 `.ai/skills/` 或 `.dsh/skills/`，Hermes 侧始终加载不到也不报错 | Hermes 的项目技能根只有 `.agents/skills/` 与 `.hermes/skills/` | 改用 `.agents/skills/`，或把该目录写进 profile 的 `skills.external_dirs`（外部档） |
| 部署克隆里的技能内容比真源新 | 有人在克隆上直接改过正文（克隆本该只拉不推） | 方向是并入真源：两侧备份 → 把克隆的新版 `SKILL.md` 与只存在于克隆的支持文件复制进真源 → 归一化逐文件比对 → 同步 README 索引的版本列 → 路径限定提交 → `git fetch && git reset --hard origin/dev` 让克隆回到镜像；**不要**用真源覆盖克隆 |
| 判「有没有绑定表」时 grep 一个标题词得到 0 | 绑定表标题不统一（`工作群绑定表` / `绑定表（…取值用）`） | 按表内键判定（`小结目录`/`看板`/`仓库根`），或用 `grep -lE '绑定表|绑定值'` 取候选后逐个人工确认 |

#### 10. Agent 生成自检清单

- [ ] 先判是否处于维护期：维护期只报待处理处数、不落盘（第 8 节）
- [ ] 本次触碰的每一处副本都归属某个已登记的目标技能根，且该根已在本机目标清单里
- [ ] 落盘前跑过 `--dry-run` 并逐目标读过明细，没有直接落盘
- [ ] 落盘后 `--dry-run` 归零；外部技能 `--verify` 退 0
- [ ] 没有手工修改任何副本（要改的在真源改）
- [ ] 本次写入的所有副本行尾为 LF
- [ ] 场景二里每一处差异都归了类并写下动作，删除项已确认没有被其它目标或文档引用
- [ ] 项目根路由表登记了全部技能、路径指向真实文件，且写明权威源是本仓
- [ ] 涉及 Hermes 时：各 profile 的 `external_dirs` 指向本机克隆、本地无同名副本残留、加载器能列出这些技能
- [ ] 项目副本口径已选定并执行到位：真源唯一模式下未 trust 该仓库且相关 profile 设了 `skills.project_discovery: false`；项目副本模式下已 trust 且副本已同步到最新

- [ ] 提交后各仓同一文件 blob sha 一致；未推送的部分已明确告知用户
- [ ] 报告只在会话里给出（逐目标明细、核验结论、提交状态、待用户定夺项），没有往仓库里写部署文档
