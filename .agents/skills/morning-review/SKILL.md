# 开工回顾

本技能描述一次开工回顾的完整流程：读出上一次收工留下的小结，检查任务队列、仓库与计划文档的当下状态，把「上次做到哪、现在什么状况、今天先做什么、哪些事在等人拍板」四件事一次说清，然后停下来等指令。它只做回顾与汇报，不写记录、不提交、不派发任务。

正文是跨工作群通用流程，双花括号包裹的占位符表示此处取各工作群的绑定值，取值与缺失处理见 `docs/spec/workgroup-binding.md`；正文自身不含仓库路径、看板名、分支名与提交身份。

## 0. 触发条件与适用范围

触发时机：用户以开工语打招呼，中文如「上班」「上班啦」「开工」「回顾」「回顾一下」「开始工作」，英文如 `morning`、`start of day`、`review`。此时按本文第 2 节的顺序走完整流程。

不适用：用户已经给出具体任务时不要先走这套流程，直接执行任务；回顾是汇报，不是执行的跳板。收工那一侧的动作见 `eod-wrapup`，本技能不写小结、不提交、不更新计划文档。若工作群没有绑定表，先按 `docs/spec/workgroup-binding.md` 落表，再执行本流程。

## 1. 绑定值

本技能使用 `{{工作群}}`、`{{汇报对象}}`、`{{仓库根}}`、`{{小结目录}}`、`{{小结命名}}`、`{{计划目录}}`、`{{决策目录}}`、`{{看板}}`、`{{分支}}`、`{{构建验证命令}}`、`{{文档规范技能}}`。执行前先在本 profile 的 `SOUL.md` 绑定表里取值；未绑定的项先探测本仓的约定位置（小结 `docs/daily/<用户名>/`〔旧布局可能写作 `docs/AI-daily/<用户名>/`〕、计划 `docs/plans/<用户名>/`、决策 `docs/adr/<用户名>/`），找到即按发现值执行并在汇报中注明「发现值，未绑定」——这是读取本仓自身的目录事实，不算沿用别的工作群的值；约定位置也不存在才按缺失跳过对应步骤并注明，不得猜测、不得借用别群的取值。

## 2. 流程（按序执行）

### Step 1：读最近一次小结

在小结目录下取最新的一份小结并用 `read_file` 完整读取：

```
search_files(pattern="*.md", target="files", path="{{仓库根}}/{{小结目录}}")
```

**按文件名的日期排序取最新，不依赖文件系统的修改时间**——批量补写的文件 mtime 往往相同，按时间排序的结果不确定；`ls -t` 在同秒写入时也会漏检，需要看目录时用 `ls -1 | sort -r`。当日小结与专题记录都以 `YYYY-MM-DD` 开头，因此按文件名排序即按日期排序。

小结目录为空时如实报告「没有找到上次小结」，直接进入 Step 2，**不要编造回顾内容**；最新小结日期明显早于最近的提交时，用 `git log --oneline --since="N days ago"` 交叉验证是记录漏写还是真的停工，并在汇报里说明是哪种。

小结里的「阻塞」与「次日计划」是前一天收工时的快照，不是当下状态：读完小结后逐条实测其外部前置（包发没发到源、上游依赖落没落地、人工门过没过）——owner 在会话之外工作，昨天的人工门可能今早已解除。前置已满足的在汇报里标注「阻塞已解除（今晨实测）」并顺势把对应任务提为今日首选项；未满足的保持阻塞。照抄阻塞清单不复核，会让当日第 1 条建议指向一个早已不存在的门。

其中「提交还没推送」这类门一律自己量，不看小结写了多少笔：

```bash
git rev-list --left-right --count @{u}...HEAD   # 左=落后 右=领先，0\t0 即已同步
git reflog show @{u} | head -3                  # 出现 update by push 即推送确实发生过
```

两侧都是 0 时写「阻塞已解除（今晨实测）：已全部落到远端」，不要把小结里的「待推送 N 笔」抄进汇报——owner 常在收工后自己补推，那个数字到开工时就已过期。

### Step 2：体检当前状态

按下列顺序逐项检查，每项都要有当下的实测结果，不能凭上一轮的印象作答。

1. **派发器**：现行架构是一个 host 一个 gateway 服务全部 profile，因此 `hermes gateway status` 对本 profile 报的消息（可能是「Gateway is not running」，也可能是「Gateway is running via the default-profile multiplexer」）**只说明本 profile 自己的 gateway 状态，不能据此判断派发停没停**。真正的判据是任务队列的派发器单例锁有没有被持有，判定分两步，第二步不可省：

   ```bash
   fuser -v ~/.hermes/kanban/.dispatcher.lock 2>&1 | head -3   # 持有者 PID（ACCESS 列的 F 即已 flock）
   hermes gateway status 2>&1 | head -15                       # 把 PID 认到 profile 名下
   ```

   非默认 profile 下 `hermes gateway status` 会把各 profile 的 gateway PID 列在 `Other profiles:` 一节里；用那里的 PID 与 `fuser` 的 PID 对齐，即可写出「持有者 = 某 profile 的 gateway」。锁被任何一个 profile 的 gateway 持有时，该 gateway 就是本 host 全部 board 的派发者；**无人持有该锁才是真异常**，此时新建的任务是永远不会被派发的僵尸任务，须先起 host gateway。

   不要用 `ls -l /proc/[0-9]*/fd | grep dispatcher.lock` 当认人判据：它给出的编号列要你自己从 `ls -l` 的行里解析，而那行里根本没有 `/proc/<pid>/fd` 这段路径，手写 sed 极易解析出垃圾；且该编号可能是 `ps -p` 查不到的进程（PID 命名空间内的 init 等），照它写汇报会写到不存在的 PID。它只配当「锁大概被持有着」的粗信号，认人一律用上面两条命令。

2. **看板**（本工作群绑定了 `{{看板}}` 时）：列任务与统计各看一次，一律用环境变量 `HERMES_KANBAN_BOARD={{看板}}` 前缀指定——`--board` 不是 kanban 子命令的合法参数（实测 `hermes kanban list --board <slug>` 报 `unrecognized arguments: --board` 直接失败），board 选择只认环境变量；`boards list` 尾行的 `Current board:` 可能指向别的 board，不可作为「当前就是目标 board」的依据；`hermes kanban boards switch` 是显示已切换而实际未变的**假开关**，一律不要依赖它。**统计各状态张数时不要给 `kanban list` 加额外参数**——`--limit`、`--board` 一类非法参数会被拒并回吐顶层 usage 全文，看上去像整条命令挂了，实际只是参数不认；照原样跑列表，用状态列计数：`hermes kanban list | awk '{print $3}' | sort | uniq -c`。看板为空是正常状态，注明即可。用户要求核查是否串板时，逐个 board 拉统计比对各任务的 assignee 归属，而不是只看当前 board。blocked 任务不要只报状态：用 `HERMES_KANBAN_BOARD={{看板}} hermes kanban show <task-id>` 读阻塞理由与诊断，理由已被后续决策或新计划覆盖的（典型：阻塞后另立了新任务书或新计划替代了当时的阻断原因），在建议事项里写「作废重开或重写任务书」，不当真阻塞上报——过期的阻塞理由会误导当日排程。

   另有一类残渣要单独识别：**自动拆卡留下的僵尸子树**——父卡被失败判死后 blocked，它的子卡全部停在 todo，而子卡的内容早已由另一条路线交付并提交。判定三步：`show` 父卡看 `children`、创建者（auto-decomposer 一类）与失败诊断；拿子卡标题去 `git log --oneline` 与最近小结里比对；再到决策/分析目录确认哪一项子交付**确实没有对应物**。汇报写成「僵尸子树 N 张，其中 M 张内容已被提交覆盖（建议删或归档），剩下一项『…』无对应物，建议重开一张干净的卡」，并注明父卡 blocked 时子卡永远不会被派发，所以它不影响派发器健康、不是事故。

3. **仓库**：取当前分支与最近几条提交：

   ```bash
   cd {{仓库根}}
   git branch --show-current
   git log --oneline -5
   ```

   在 WSL 挂载的 Windows 盘（`/mnt/<盘符>/...`）上的仓库里，`git status --short` 可能耗时数十秒，**不要把它放进汇报主流程**；确需查看未提交文件时，用 `execute_code` 配 120 秒以上超时单独跑。工作树脏是体检异常项，要写进汇报的关注列表；抽一条 diff 看内容定性归属（IDE 自动补的包引用、worker 遗留改动、用户手改），汇报里写归属与处置建议（入库/丢弃/待确认），只写「工作树脏」用户无法处置。

4. **计划与决策**：在 `{{仓库根}}/{{计划目录}}` 下取最近修改的计划文档，读其中的步骤状态与验收标准。计划文件命名随工作群而定（有 `PLAN-<四位>-<slug>.md` 形式，也有 `adr-<编号>-<slug>.md` 形式），用 `ls -1t` 列目录取最新 `.md`，不要按固定前缀匹配——前缀对不上会把活跃计划整份漏掉；在 `{{仓库根}}/{{决策目录}}` 下按多关键字检索决策记录：`grep -rliE "Proposed|提案|Discussion Draft|未拍板|待拍板"`，**不要只匹配英文也不要只匹配头部表格**——状态写法并存多种：英文表格行（`| 状态 | Accepted |`）、中文小节（`## 状态`）、中文引用块行（`> 状态：提案（Discussion Draft，供研讨，未拍板）`），单关键字 `Proposed` 会把中文状态整份漏检；grep 空结果不等于无开放决策，再对最近修改的几份决策记录直接读头部状态行复核。状态仍为 `Proposed` 的决策是等用户拍板的方向性问题，**未拍板前不得派发相关实现**，且必须在汇报里点名，读了不报等于没读。已拍板但尚未落地实施的决策（状态行已改「已拍板」、文档末尾链接了 plan）是比「待拍板」更常见的今日候选——逐个列出并附 plan 路径，不要只盯 Proposed。

   计划的 `status` 元数据可能过时：用户可能在 IDE 或其他会话里已经完成并提交，而计划文件没更新。发现提交内容与计划条目吻合却仍标 `proposed` 时，标注「⚠️ 可能已完成」并建议用户确认，不要直接改计划状态。

   同样的滞后还会出现在 ADR／决策记录的**头部状态行**上：状态写着 Accepted，括号里却仍挂着「尚未派发」一类施工期措辞，而对应批次早已合入。汇报时按「状态已定、正文措辞待更正」列出，并注明不改冻结文档正文——过期措辞会让人以为活还没开工。

   反过来也有一坑：计划与 ADR 的「进度记录」是按日期追加的日志，早期段落里的「待拍板／Proposed」只描述当时那一刻，同一节后面的段落往往已写「已拍板并冻结」。报「待拍板项」之前先读命中行之后 3-5 段与文档末段，按**当前状态**下结论；把历史状态当未决项报，会让 owner 去核对一件早已定下的事，也会误伤写记录的人。

   会话中 freshly 拍板的设计（当轮对话里用户刚逐条给出决定）在下次开工时不一定已写进文档——开工回顾时，把上一次收工后用户在对话里的最新拍板与决策文档头部状态对齐，不一致时以对话为准并在汇报中说明文档待更新；反之，不要拿本会话的记忆当档案事实，汇报一律以文档与看板实测为准。

5. **构建与测试基线**（绑定了 `{{构建验证命令}}` 时）：跑一次构建，把警告数、错误数与测试结果作为当日基线写进汇报；项目专有的能力面检查（例如引擎能力掩码、注入的实现类）不属于本技能的通用流程，由该工作群自己的技能或任务描述承担。**沿昨日基线的合法条件是「其后零提交且工作树干净」**——工作树有未提交改动（哪怕只是 csproj 里 IDE 自动补的包引用）就不得沿用上次数字，必须重跑或注明「未重跑，其前提是零提交」的限定；「没有新提交」不等于「代码没变」，拿脏树的昨日数字当基线是假基线。工作树大、全量构建分钟级时，可在汇报里写「基线未重跑（代码零提交，数字无变化依据）」并让当日首个任务验收时补真基线，但不得写成实测值。

   基线是与上次小结记下的数字对照看的，不是只看"全绿"：通过项数只增不减，**跳过数变大也是异常**。真机／真链路类用例常以"本机没有接口就静默返回"或留痕跳过收场，于是刚重启过的机器上会跑出一份更小的绿——先查前提（例如 `ip -brief link | grep vcan`），缺了就按该工作群的链路技能重建后**复跑一遍再写基线**，并在汇报里说明"首次跑因前提缺失而少了 N 项、补齐后为 M 项"。不做这一步，汇报的基线就是假的。

   构建红了时除错误摘要外加一行定性：`git log --oneline -3 -- <报错文件>` 定位引入提交；看同目录同级文件拿正确范式（同一接口的兄弟实现通常就是现成写法）；汇报里写引入者（提交+作者）与建议修法。按「回顾不执行」原则不自行修复——主干上的红常是其他工程师的提交，先定性再等用户指派，避免修错归属。

### Step 3：向 `{{汇报对象}}` 汇报

直接在对话里输出，不写文件。**输出渠道是终端时把下面这份结构改写成纯文本**：标题自占一行、层级用缩进、分隔用空行或 `▍` 一类行首标记；`##`、`-`、``` 这些 markdown 标记在终端里不会渲染，照抄只会得到一堆字面字符。渠道支持 markdown 时再用下面的原样结构：

```
## ☀️ {{工作群}} 今日开工 — {日期}

### 📋 上次回顾（来自 {最新的小结文件名}）

- 已完成：{N} 项
- 进行中/未完成：{N} 项
- 上次提交：{hash 或「无」}
- 缺口提示：{小结目录缺某日文件时如实说明，不代为补写}

### 📊 当前状态

- 派发器：{持有单例锁的 profile / 无人持有}
- 看板（board {{看板}}）：{总数} 任务 / {进行中} 运行 / {阻塞} 阻塞
- 仓库：分支 {branch}，最近提交 {hash}
- 当前计划：{PLAN-xxxx 名称 + 批次进度}
- 构建与测试：{build 警告/错误数，测试结果}

### 🎯 今日建议事项

1. {上次小结「次日计划」中优先级最高的一项}
2. {看板中待办或被阻塞任务里优先级最高的一项}
3. {等待用户拍板的决策项}

### ⚠️ 需要关注

- {状态为 Proposed 的决策：未拍板前不得派发相关实现}
- {阻塞或超期的计划项}
- {体检异常：无人持有派发锁、小结目录缺日、工作树脏、构建失败}
```

构建失败时标为最高优先级并给出错误摘要与定性（引入提交+建议修法，见 Step 2 第 5 条）；汇报里的每一项都要能追溯到本次实测，没有实测到的项写「未采集」，不要用推测填满。

### Step 4：停下等指令

汇报完等用户下任务。**这是回顾与汇报，不是执行**：即使看到待办或被阻塞的任务，也先汇报、等确认，不自行派发、不顺手开始修。

## 3. 边界情况

1. **没有小结**：如实报告，跳到 Step 2，不编造回顾内容。
2. **最新小结不是上一次工作的日期**：注明「最新小结是 {日期}，距上次工作已 {N} 天」，并说明该目录是否按日记录。
3. **看板为空**：正常状态，注明即可；不要因为空就跳过看板检查而不报数字。
4. **派发器锁无人持有**：这是真异常，按 Step 2 第 1 条处置，不要因为「gateway status 报本 profile 未运行」就判定派发停了。
5. **WSL 仓库慢**：优先 `git log --oneline`，避开 `git status`；必须查时用 `execute_code` 配 120 秒以上超时。
6. **未绑定看板、决策目录或构建命令**：跳过对应步骤，在汇报里注明「本工作群未绑定 X」，不要沿用别的工作群的值，也不要静默省略。
7. **不要自动派发任务**：等用户确认。

## 4. 自检清单

交付汇报前逐条核对：

- [ ] 最新小结是按文件名日期取的，且已完整读过，不是只看文件名
- [ ] 汇报里的分支、提交 hash、看板数字、构建结果都是本次实测值，没有沿用上一轮的印象
- [ ] 测试项数与上次小结对照过：通过数只增不减，跳过数的增加已查明原因并补齐前提后复跑
- [ ] 基线沿用了昨日数字时，已确认其后零提交且工作树干净；工作树有未提交改动则重跑过构建
- [ ] 派发器结论依据单例锁的持有者，而不是本 profile 的 gateway 状态
- [ ] blocked 卡已区分三种情形：真阻塞 / 前置已解除（附实测命令与结果）/ 僵尸子树（含无对应物的那一项）
- [ ] 状态为 `Proposed`/「提案（未拍板）」的决策已逐条列出，未漏报
- [ ] 小结目录的缺口、工作树是否干净等异常已在「需要关注」中如实说明，没有代为补写
- [ ] 未绑定的项已注明，没有借用别的工作群的取值
- [ ] 汇报完成后停下等指令，没有自行派发或开工
