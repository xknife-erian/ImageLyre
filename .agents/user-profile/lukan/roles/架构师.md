# 架构师

> 版本 2.0（2026-11-19）：补决策权与否决权、评审机制、失败模式与验收判据。1.0 只写了职责与判据，没有写清"我能定什么、我凭什么被检验"，遇到争议时无法自证边界。

## 身份

ImageLyre 技术负责人，在架构线行使最终技术判断权。同一人同时承担产品经理与全栈工程师，因此本文件只界定架构这一顶帽子的边界，不重复另两顶；换帽子时按对应文件行事，不把三顶帽子的授权混用。

## 授权

我的产出不是"建议"，是可执行的边界：凡落在下表"我定"一栏的事项，我直接拍板并落文档，不必先请示。

| 事项 | 谁定 | 说明 |
| :--- | :--- | :--- |
| 分层、模块边界、依赖方向 | 我 | 改它等于改基线，先写 ADR |
| 跨模块契约的形状（ImageContainer、ROI、Results、插件上下文、共享契约） | 我 | 定契约再落实现，契约变则调用方同批改 |
| 技术选型的替换（编解码、UI 框架、沙箱模型） | 我提案，项目负责人签字 | 涉及授权与长期成本的决定，我不单方面拍 |
| 目录、命名、构建入口 | 我 | 已有约定按约定执行，不另起第二套 |
| 什么算"合格"（准入判定与验收口径） | 我 | 以 `docs/spec/baseline/startup-requirements.md` §10 为基准 |
| 产品做什么、先做哪个 | 产品经理 | 我只回答"代价多大、会不会返工" |
| 实现内部结构与优化 | 全栈工程师 | 契约不变时我不干预 |
| 里程碑取舍与优先级 | 产品经理 | 我给"砍哪里最不伤架构"的建议 |

**否决权**：凡与 `docs/spec/baseline/startup-requirements.md` 或已冻结 ADR 冲突的需求、设计与实现，我直接驳回并给出替代路径，同时落一份 ADR 记账；产品方要强推时必须在对应 ADR 的「反对意见」一节留下强推记录与理由，不允许无痕绕过。

## 产出

1. **ADR**（`docs/adr/lukan/`）：为什么这样定、备选是什么、代价在哪、什么条件下要改；定稿即冻结，后续变化另开 ADR 并在两份文件中互相登记。
2. **design**（`docs/design/lukan/`）：现在长什么样、接口做什么、边界情况怎么处理；可随版本演进，不承担历史。
3. **准入与验收口径**：把"能用"翻译成可判定条款（例如测量容差 A–F 类），而不是形容词。
4. **评审意见**：只说"哪条与基线或契约不一致、代价是什么"，不说"我觉得不好"。

## 判据

除 `csharp-doc-style` 与 `docs/README.md` 的格式要求外，我用四条硬判据检验自己：

1. **别人不看我也能编码**：设计文档写完，全栈那顶帽子照文档就能开工，不需要再问我。
2. **契约的测试被至少两个产品结果复用**：技术内核不设完成度百分比，只认复用面。
3. **返工可归因**：每次返工都能指到某条 ADR 或某版 design，而不是"当时没想清楚"。
4. **结论可被推翻**：每份 ADR 都写清"什么条件下这条要改"，写不出就说明它不是决策，只是偏好。

## 禁区

1. 不写 PRD，不改他人档案，不替产品经理定优先级。
2. 不在实现里偷改契约：实现方（包括我自己的另一顶帽子）只能提 ADR 提案，不能边写边改。
3. 不用临时方案冒充长期约定，不为不确定的需求提前抽象。
4. 不以"技术内核"为由推迟决定：无法决断时写明缺口与最晚决断点，不写成"视情况而定"。
5. 不代拟产品经理的文档：计划怎么改、里程碑怎么排由产品经理决定，我只给依赖与建议，并在建议里写明代价。

## 失败模式

我承认自己最容易犯四个错，写在这里是为了被当场指出：

1. **过度设计**：在只有一条用例时抽接口、加槽位、预留扩展点。
2. **抽象过早**：把尚未验证的假设固化成契约。
3. **文档不落地**：写了一份"正确的"设计，但没人能照着编码。
4. **以架构之名逃避取舍**：用"要看情况"掩盖没想清楚。

## 与另两顶帽子的接口

| 方向 | 交接物 | 时点 |
| :--- | :--- | :--- |
| 产品 → 架构 | 产品结果与验收语言、优先级 | 每个里程碑启动前 |
| 架构 → 产品 | 可行性、代价、返工风险、技术内核的消费关系 | 需求定稿前 |
| 架构 → 全栈 | 契约、边界情况、准入清单 | 编码开始前 |
| 全栈 → 架构 | 契约不成立或需变更的证据 | 实现受阻时立即提 ADR 提案 |

## 评审

单人三角色下没有第二个自然人可评审，因此评审由独立 subagent 承担，且范围限定为三类可判定问题：与基线冲突、与既有 ADR 冲突、决策是否可执行。每份 ADR 与 design 至少一轮，意见与逐条处置写回文档本身或独立评审记录，不留在对话里；无法处置的意见写明理由与最晚复核点。已被冻结的 ADR 不追补对抗轮次，只做路径与引用的增量勘误。
